design-code / phase 2 - pick an approach

Harness adapters: how does a worker's state reach flow without the mod?

Goal: flow learns what each worker does from the harness itself, deterministically. The skills stop knowing about flow, the flows mod's reporting goes away, and other harnesses (Codex, pi) can follow with their own adapter. The three approaches differ in who receives the harness's events and who turns them into flow events.

What exists today

  • A worker reports through the flows mod (claude-code-mods): it watches engine events and runs flow report --flow $FLOW_ID ... one at a time (flows/hooks/register.tsx:132-150), with the mapping in reporter.ts.
  • Each phase skill also carries a "if a flow command exists, report ..." block (agent-skills/skills/*/SKILL.md), so phases arrive twice today.
  • flow report appends one Event to the flow's log; the fold is idempotent, so repeats are harmless (main.rs:433, fold.rs).
  • flow ui's server launches every worker from launch::worker_spec and the agent's command template in config.toml (launch.rs, config.rs), with FLOW_ID in its environment.
  • The server already knows each pane's liveness (running, exited, failed) and the peek already reads Claude's transcript (server/host.rs, ui/peek.rs).
  • The flow log is the single source of truth; every reader goes through fold.

A. A flow hook command: the harness calls flow, flow translates recommended

flow ui launches a Claude worker with --settings hooks that run flow hook claude-code on each event. That command reads the hook's JSON from stdin, turns it into zero or more flow events through the agent's adapter, and appends them to the log of $FLOW_ID. The adapter is a pure function per harness, plus the argv it adds at launch.

How it works: only hooks, no model involved

A hook is a shell command that Claude Code the program runs on its own whenever an event happens. The model is not asked, does not see the hook, and cannot skip it. Its output is empty, so nothing enters the conversation.

  1. flow ui starts the worker as claude ... --settings '<json>'. The JSON is the only wiring, written by flow; nothing is installed, the user's own settings stay as they are: 
    { "hooks": {
    "UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "/…/flow hook claude-code" }] }],
    "PreToolUse":       [{ "matcher": "*", "hooks": [{ "type": "command", "command": "/…/flow hook claude-code" }] }],
    "PostToolUse":      [ …same… ],
    "Stop":             [ …same… ],
    "Notification":     [ …same… ],
    "SessionEnd":       [ …same… ] } }
  2. You type a prompt. Before the model even starts, Claude Code runs flow hook claude-code with {"hook_event_name":"UserPromptSubmit", …} on stdin. flow appends working to the log of $FLOW_ID.
  3. The model calls the Skill tool for design-code. Claude Code runs the hook with {"tool_name":"Skill","tool_input":{"skill":"design-code"}}; flow looks the skill up in its phase map and appends phase design. The skill text says nothing about flow.
  4. The model finishes its turn. Claude Code runs the hook with {"hook_event_name":"Stop","last_assistant_message":"…?"}; flow appends waiting "<the question>".
  5. You /exit: SessionEnd with prompt_input_exit, flow appends ended. A hangup (other) appends nothing, so the flow resumes.

So "the harness calls flow" means exactly this: Claude Code runs a command flow told it to run. Every decision is a fixed rule in flow's Rust code, tested against the recorded payloads.

Touches

  • new src/adapter.rs (or adapter/ with one file per harness)
  • main.rs: flow hook <adapter> (hidden, like flow server)
  • config.rs: Agent.adapter, a skill-to-phase map
  • launch.rs: the wiring argv in worker_spec and resume

Fit

  • Same shape as flow report: CLI in, Store::append out, the log stays the only truth.
  • Pure translation like fold.rs and launch.rs: table tests over the recorded hook JSON.
  • Works for any harness that can run a command: Codex's notify, a pi extension, a plain shell.
Gains
  • Deterministic: the harness fires hooks, the model never decides to report.
  • No state between calls, so nothing to keep in sync; order kept by running the hooks synchronously.
  • Independent of flow ui: a log written with the server down still counts.
Costs
  • One short flow process per hook (a few ms; two per tool call).
  • Stateless, so it cannot suppress a repeated "waiting"; the fold already absorbs repeats.
  • Subagent turns must be filtered by agent_id in each call.

B. Hooks talk to flow server; the server translates

The worker's hooks send events to the running flow server (Claude Code's http hook type to a local endpoint, or flow hook forwarding over the socket). The server translates with state per worker (running subagents, last report) and appends to the log.

Gains
  • Translation can keep state: dedupe, count subagents, combine with pane liveness.
  • With http hooks there is no process spawn per event.
Costs
  • Reporting only works while the server runs; events during a server restart are lost.
  • An HTTP listener in the server (new dependency, a port) or a second socket protocol; more on the one thread that owns all state.
  • Every other harness has to reach the server too; most can only run a command.

C. No hooks: the server reads each worker's transcript

The server tails each worker's transcript (as the peek already does) and derives state: a tool_use of Agent is delegated, the last assistant message without a following prompt is waiting, a Skill call sets the phase.

Gains
  • Nothing to wire into the harness at all.
  • Works for any harness that writes a transcript.
Costs
  • Not deterministic: "the turn ended" and "waiting for permission" are not in the transcript, they are inferred; /exit vs a hangup is invisible.
  • Polling and parsing large files (attachments of 100 KiB+) for every worker.
  • The transcript format is private to each harness and changes without notice.

Kept from C regardless of the choice: the server's own liveness (running / exited) stays the fallback for a harness without hooks.

Other harnesses

Built now: Claude Code only. The architecture only has to let the next adapter plug in. Checked today against their source, so the shape holds:

  • Codex has lifecycle hooks (on by default) that receive a JSON object on stdin, with nearly Claude's events: UserPromptSubmit, Pre/PostToolUse (shell is Bash), Stop with last_assistant_message, SessionEnd. A codex adapter is one more translate function behind the same command. Its wiring differs (per-run -c config, hook trust).
  • pi has TypeScript extensions loaded per run with -e; one tiny extension would run flow hook pi. It has no subagents and starts with a fixed --session-id, like Claude.
  • Neither has a "skill started" event; phases come from the prompt text there, which the phase map handles the same way.

A and its command fit all three; B needs each harness to reach the server; C needs a transcript parser per harness.

A and B see the same things, but A never misses one; the overview is only as good as its gaps. What makes the overview richer is the set of events flow translates. These come with A, whichever you pick:

  • Permission vs question: "waiting for permission: Bash(rm -rf build)" from Notification permission_prompt and the pending tool, apart from "waiting: Which approach?".
  • The question itself from AskUserQuestion and Stop's last message, not a guess from the screen.
  • Subagents named by their description while they run, ignored once their own events carry agent_id.
  • Phases from any skill set through a phase map in config, so other people's skills get the steps bar too.

Recommendation: A

A is the only approach that is both deterministic and harness-agnostic: every harness worth supporting can run a command, and a command that appends to the log is exactly what flow report already is. It keeps the log as the single truth and works even while flow ui is down. Its one weakness, statelessness, does not matter because the fold already tolerates repeats, and the only state the mod kept (running subagents) is replaced by the agent_id field Claude Code puts on every subagent event.
