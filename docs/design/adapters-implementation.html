design-code / phase 3 - review the implementation

Harness adapters: a worker reports through Claude Code's own hooks

new modified unchanged

1. Decision recap

Approach A: flow ui launches a Claude Code worker with --settings hooks that run flow hook claude-code on each event; that command translates the hook's JSON into flow events with a pure adapter and appends only what changes the flow. No model decides anything, the skills stop knowing about flow, and the flows mod's reporting can go.

Decided in phase 2: Claude Code only now; the structure takes Codex or pi later as one more adapter behind the same command. The event log stays the only truth.

2. Structure overview

3. Units

src/adapter/mod.rs new

Which harnesses flow can observe, and the two things each one does: wire itself into a launch, translate one event. Pure.

/// A harness flow observes through its own hooks.
pub enum Adapter { ClaudeCode }

impl Adapter {
    /// "claude-code" -> ClaudeCode; None for a name flow does not know.
    pub fn named(name: &str) -> Option<Adapter>;
    pub fn name(self) -> &'static str;
    /// The arguments that make the harness report to `<flow_exe> hook <name>`,
    /// inserted right after the program in the agent's argv (fresh and resumed).
    pub fn wiring(self, flow_exe: &Path) -> Vec<String>;
    /// The flow events one hook payload means; empty for an event that means nothing.
    pub fn translate(self, payload: &Value, phases: &PhaseMap) -> Vec<EventKind>;
}

src/adapter/claude_code.rs new

Claude Code's hook settings and the mapping from its hook JSON to flow events. Pure; every rule is a table test over recorded payloads.

/// The --settings JSON: UserPromptSubmit, PreToolUse, PostToolUse, PermissionRequest, Stop and
/// SessionEnd each run `<flow_exe> hook claude-code` (exec form, synchronous, timeout 10 s).
pub fn settings(flow_exe: &Path) -> String;

/// Ignores every event a subagent raises (agent_id set). Otherwise:
///   UserPromptSubmit             -> working; plus phase when the prompt is a typed /skill
///   PreToolUse Skill             -> phase of tool_input.skill
///   PreToolUse Agent             -> delegated tool_input.description (not when run_in_background)
///   PreToolUse AskUserQuestion   -> waiting questions[0].question
///   PostToolUse (any tool)       -> working
///   PostToolUse plan-progress    -> tasks done total, or blocked "item: note"
///   PostToolUse Bash             -> merge-request url, when gh pr / glab mr create printed one
///   PermissionRequest            -> waiting "permission: Name(target)"; nothing for AskUserQuestion
///   Stop (stop_hook_active false)-> waiting question(last_assistant_message), else "turn ended"
///   SessionEnd prompt_input_exit -> ended; any other reason (hangup = "other") -> nothing
pub fn translate(payload: &Value, phases: &PhaseMap) -> Vec<EventKind>;

/// The last sentence ending in "?" of the answer's last line, else its last sentence (the mod's rule).
fn waiting_question(answer: &str) -> Option<String>;
/// "ok, 4/9 done" or "ok, all 9 done" -> (4, 9) / (9, 9).
fn task_counts(result: &str) -> Option<(u32, u32)>;
/// gh pr create / glab mr create and the first http(s) URL in its stdout.
fn created_merge_request(command: &str, stdout: &str) -> Option<String>;
/// The skill a prompt typed as "/name args" names.
fn typed_skill(prompt: &str) -> Option<&str>;
/// Name(target) for a permission question: Bash(command), Write(file_path), ...
fn tool_call(name: &str, input: &Value) -> String;

  • config.toml gains adapter = "claude-code" per agent and a [phases] table: 
    [phases]

review-changes = "review"
write-merge-request = "merge-request"
  • Hook input (Claude Code -> flow hook, stdin): the payloads recorded today, kept as fixtures in src/adapter/fixtures/claude-code/*.json.
  • Wiring (flow -> Claude Code, argv): --settings '{"hooks":{...}}', inline, nothing written to disk.

5. Call chains

a. flow ui opens a worker

  1. Server::open_worker -> launch::worker_spec(flow, agent, env): Option<PaneSpec>
  2. worker_spec -> Adapter::named(agent.adapter): Option<Adapter>
  3. worker_spec -> Adapter::wiring(env.flow_exe): ["--settings", "{...}"], inserted after argv[0]
  4. Server -> Host::open(spec): claude --settings '{...}' -n shop-217 --session-id <id> "/ship-feature ..." with FLOW_ID
  5. Error: unknown adapter name -> reconcile puts it in Wanted.failed -> Host::fail(key, "agent claude uses adapter X, which flow does not know"); the sidebar shows failed with that reason.

b. A hook event reaches the log

  1. Claude Code runs flow hook claude-code with the event JSON on stdin, FLOW_ID inherited
  2. main -> hook(store, config, "claude-code", flow_id, stdin, now): Document::Silent
  3. hook -> Adapter::named("claude-code") -> Adapter::translate(payload, &config.phases): Vec<EventKind>
  4. hook -> fold::resolve(flows, flow_id), then per kind Store::events(id) -> fold::changes(id, events, kind, now): bool
  5. when true: Store::append(id, Event::new(now, kind)); exit 0, no stdout
  6. Errors: no FLOW_ID (a session flow did not start) -> nothing. Unknown adapter, unparsable JSON, no such flow, a failed append -> one line on stderr (Claude Code's debug log), nothing appended, exit 0. The worker is never slowed or blocked by flow.

6. Conventions followed

  • A hidden subcommand for something only a program calls, like flow server (main.rs #[command(hide = true)]).
  • Pure units with table tests, I/O in main: like launch.rs and fold.rs; main stays the only reader of the environment and stdin (CLAUDE.md).
  • Built-in defaults merged with the file, file wins: like builtin_agents in Config::load.
  • Rules ported from the mod (reporter.ts: waitingQuestion, taskCounts, createdMergeRequest, phaseOfSkill, the 200-char cut) so behaviour carries over.
  • Deviation: flow hook skips events that change nothing (the mod appended every one), so a long session does not grow its log by a line per tool call.

7. Test seams

  • claude_code::translate: one table test per row of chain c, over the recorded payloads (fixtures); helpers each with their own cases (the mod's tests ported).
  • Adapter::wiring / settings: the JSON parses and names every event with the exe path; worker_spec puts it after the program, fresh and resumed.
  • fold::changes: repeats and no-ops are false, real changes true.
  • tests/cli.rs: flow hook claude-code with a payload on stdin writes the event, prints nothing, exits 0 also without FLOW_ID and with garbage.
  • End to end: a real Claude worker in flow ui, with the flows mod switched off, shows phase, delegated, the question, a permission wait and ended.

8. Assumptions

  1. Only workers are wired; the master has no FLOW_ID, so wiring it would only start processes that do nothing.
  2. Hooks run synchronously (keeps the order of events); each flow hook takes a few ms. Timeout 10 s.
  3. No heartbeat: under flow ui the server already sees whether a worker's process lives; "not responding" then only comes from flows with heartbeats (flow report heartbeat stays).
  4. A permission wait is stored as Waiting with the text permission: Name(target), not a new event kind.
  5. Any main-agent PostToolUse means working (after a permission or a question was answered); fold::changes keeps it to one line.
  6. Workers started before this change get the wiring on their next resume (the resume argv is wired too).
  7. flow report stays as it is, for scripts and other tools.
  8. The recorded payloads are from Claude Code 2.1.299; an unknown event or field is ignored, never an error.

9. Open questions

1. Which skills map to phases by default?

The map lives in config.toml either way. Recommended: ship your four as the built-in default, so nothing changes for you and anyone else can override or add.

2. Retire the old reporting in the same plan?

Recommended: yes, as the last tasks, after the end-to-end check passes: remove the reporting from the flows mod (claude-code-mods) and the "report to flow" block from the five skills (agent-skills). Until then both report; that is harmless, repeats change nothing.
