saaio 0.2.0 · approach A, focus-aware, with a bell fallback · 2026-10-27

Desktop notifications: implementation

Decision recap

The UI notices in the board diff that a flow came to Waiting or Blocked, and asks the loop to notify. A new Notifier writes one sequence, chosen once from the environment: OSC 9, OSC 777, or a plain BEL for terminals that support neither.

  • Approach A, focus-aware. A flow notifies when it is not in view or the terminal has lost focus.
  • saaio keeps focus reporting on itself. A pane that asked for focus events gets them byte for byte as today.
  • BEL fallback for terminals without OSC notifications that saaio recognises: Alacritty and Terminal.app. The docs show Alacritty's [bell] command.

Units

src/ui/notify.rs new

Writes one desktop notification to the real terminal in the way it understands. Sibling of clipboard.rs.

//! `Notifier`: desktop notifications through the terminal, by OSC 9, OSC 777 or its bell

/// How the terminal saaio ui runs in is told to notify.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Sequence {
    /// ESC ] 9 ; saaio: text BEL - iTerm2, Ghostty, WezTerm, kitty, and the default.
    Osc9,
    /// ESC ] 777 ; notify ; saaio ; text BEL - foot, urxvt, VTE.
    Osc777,
    /// BEL alone - Alacritty, Terminal.app: no text, the terminal's own bell handling.
    Bell,
}

impl Sequence {
    /// Bell for Alacritty ($ALACRITTY_WINDOW_ID, TERM alacritty) and Terminal.app
    /// (TERM_PROGRAM Apple_Terminal); Osc777 for TERM foot* / rxvt* or $VTE_VERSION; else Osc9.
    pub fn pick(term: Option<&str>, program: Option<&str>, vte: bool, alacritty: bool) -> Sequence;
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Notifier {
    sequence: Sequence,
    /// Inside tmux: an OSC goes through its DCS passthrough.
    tmux: bool,
}

impl Notifier {
    pub fn new(sequence: Sequence, tmux: bool) -> Notifier;

    /// Writes the notification for `text` (control characters dropped, cut to 200 chars) and
    /// flushes; Err when the terminal cannot be written.
    pub fn notify(&self, out: &mut impl Write, text: &str) -> Result<()>;
}

/// The bytes for the terminal itself, before any tmux wrapping.
fn sequence(sequence: Sequence, text: &str) -> String;
/// ESC P tmux; sequence with every ESC doubled ESC \
fn passthrough(sequence: &str) -> String;

BEL is never wrapped: tmux handles the bell itself and passes it on.

src/ui/app/notifications.rs new

Decides which state changes reach you as a notification, and what it says. Part of impl App, no I/O.

impl App {
    /// [ui] notify: whether state changes raise desktop notifications.
    pub fn set_notify(&mut self, on: bool);

    /// Effect::Notify for each worker in both boards that came to Waiting or Blocked
    /// while out of sight.
    pub(super) fn worker_notifications(&self, old: &Board, new: &Board) -> Vec<Effect>;

    /// Effect::Notify when the master came to Waiting or Blocked while out of sight.
    pub(super) fn master_notification(&self, was: Option<State>, state: Option<State>) -> Vec<Effect>;

    /// The terminal has lost focus, or `key` is not the pane in view.
    fn out_of_sight(&self, key: &PaneKey) -> bool;
}

/// Waiting or Blocked now, and not the same a moment ago.
fn calls_for_you(was: Option<State>, now: State) -> bool;

/// "shop-230 asks: Which approach?", "shop-230 waits for you",
/// "shop-230 is blocked: Bash(cargo publish)", "shop-230 is blocked".
fn worker_text(flow: &FlowView) -> String;

/// "master waits for you", "master is blocked".
fn master_text(state: State) -> String;

Data

  • Sequence: built in Env::notifier, then lives in the UI. It never crosses the socket.
  • Effect::Notify(String): App to the loop, within the UI process.
  • Routed::Focus(bool), Target.focus: Router to App, within the UI process.
  • UiConfig.notify: config.toml to the UI. The server ignores it.
  • No proto, store or --json change.

Call chains

1. A worker comes to Waiting while out of sight

sequenceDiagram
  participant S as saaio server
  participant L as ui.rs loop
  participant A as App
  participant N as Notifier
  participant T as terminal
  S->>L: ServerMsg::Board(board)
  L->>A: on_server(Board)
  A->>A: worker_notifications(old, new)
  A-->>L: [Effect::Notify(text)]
  L->>N: notify(stdout, text)
  N->>T: OSC 9 / OSC 777 / BEL (tmux-wrapped OSC)
  N--xL: Err: could not write
  L->>L: log to server.log
  1. read_server -> Event::Server(ServerMsg::Board(board))
  2. ui::run -> App::on_server(message): Vec<Effect>
  3. App::on_server -> App::worker_notifications(old, &board): Vec<Effect>. Nothing when !self.notify. Otherwise for each flow present in both boards with calls_for_you(Some(was.state), flow.state) and out_of_sight(&PaneKey::Flow(id)): Effect::Notify(worker_text(flow)).
  4. ui::run -> ui::notify(&env.notifier, &env.log, &text, clock)
  5. ui::notify -> Notifier::notify(&mut io::stdout(), text): Result<()>
  6. Error: a failed write returns Err, and ui::notify logs ui: notify failed: ... to server.log. Nothing on screen; the sidebar still shows the state.
  7. A terminal that ignores the sequence, or tmux without allow-passthrough, drops it silently. saaio cannot know this, and the docs say so.

No storm on startup: the first board has no old board, so step 3 never runs. A flow missing from the old board never notifies.

2. The terminal loses focus

  participant T as terminal
  participant R as Router
  participant A as App

  T->>R: ESC [ O
  R->>R: focus_event: Some(false)

  1. read_stdin -> Event::Input(bytes)
  2. ui::run -> Router::route(&bytes, Target { focus: modes.focus, .. }): Vec<Routed>
  3. Router::route -> focus_event(rest): Option<bool>. Bytes go into the pane's plain run only when target.focus && !target.modal, then Routed::Focus(false).
  4. ui::run -> App::on_input(Routed::Focus(false)): vec![] sets terminal_focused = false.

3. The master comes to Waiting or Blocked

  1. App::on_server(ServerMsg::Master { turn, .. }) -> App::on_master_turn(turn): Vec<Effect>
  2. App::on_master_turn -> App::master_notification(was, state): Vec<Effect>. It notifies when calls_for_you holds and out_of_sight(&PaneKey::Master). A master that comes to Idle does not notify.
  3. Then as steps 4 and 5 of chain 1.

4. config.toml changes notify

  1. ui::run (tick) -> reload_config -> ConfigWatch::changed(): Some(Ok(config))
  2. reload_config -> App::set_notify(config.ui.notify)
  3. A broken file keeps the last working setting, as for prefix.

Conventions followed

  • Notifier built from environment flags in Env, written to stdout from the loop, failure to server.log: mirrors Clipboard (src/cli/env.rs:53, src/ui/clipboard.rs:19, src/ui.rs:252).
  • Environment read only in main.rs::env() (src/main.rs:44, clippy disallowed-methods).
  • App returns effects, loop does I/O: Effect::Copy (src/ui/app/effect.rs:126).
  • Transitions from the board diff: the "changed" row light (src/ui/app/messages.rs:31).
  • saaio's own mode kept on over the pane's: mouse in captured (src/ui/outer.rs:88).
  • Config switch next to update_check, set on reload like set_prefix (src/ui.rs:313); example line checked by the existing example tests.
  • A new app/notifications.rs child rather than growing messages.rs: one responsibility per file.

Test seams

  • notify.rs: Sequence::pick per environment; exact bytes of each sequence; tmux doubles every ESC and leaves BEL alone; control characters dropped; long text cut. Writes go to a Vec<u8>.
  • input.rs: focus in and out become Routed::Focus; forwarded unchanged to a pane with 1004 and not to one without, nor under a dialog; a focus event right after the prefix leaves the prefix pending.
  • app/tests/notifications.rs (new subject): first board silent; Idle to Waiting out of view notifies once; the same board twice notifies once; in view and focused silent; in view and unfocused notifies; Waiting to Blocked notifies again; off in config silent; master Waiting out of view notifies, Idle does not.
  • outer.rs: captured keeps focus on.
  • config: the existing example tests cover notify once its line exists.
  • E2E: scratch store, UI in a PTY whose output is captured, a flow reported waiting, then blocked, then focus out on the flow in view. Assert one OSC per transition and none on start. Then the same in a real Ghostty window, to see the notification.

Assumptions

  1. Text: "shop-230 asks: <first question>", "shop-230 waits for you", "shop-230 is blocked: <blocker>", cut to 200 chars. The OSC 9 form starts with "saaio: "; OSC 777 has the title "saaio".
  2. "In view" means the pane has focus in saaio, even while the board or a dialog is open over it.
  3. Waiting to Blocked, or back, is a new transition and notifies again.
  4. A terminal that never reports focus counts as focused.
  5. Notifications for other projects' flows (the board's "all" view) are out of scope; only this UI's own board.
  6. No rate limit: each transition is one notification. Agents rarely flip faster than a person can read.
  7. BEL only for terminals saaio recognises (Alacritty, Terminal.app). An unknown terminal gets OSC 9, which costs nothing when it is ignored.

Open questions

  1. The switch: [ui] notify = true, on by default? Recommended: yes. Ignored sequences cost nothing, and the feature is the point of the roadmap row.
  2. The master: notify when it comes to Waiting or Blocked, but not when its turn ends Idle? Recommended: yes. Idle follows nearly every worker stop and would repeat the worker's own notification.
