# flow

![flow ui with four workers](docs/media/flow-ui.png)

I usually have several coding agents working at once, each on its own
feature. flow is the tool I built to keep track of them: it opens each
agent in its own git worktree, shows where every one stands, and tells me
when one needs me. I use it every day with Claude Code and Codex, and
thought it might help others too.

flow is a terminal UI, `flow ui`, and a command line whose main user is an
agent.

## Quick start

You need macOS or Linux, git, Rust 1.95 or newer, and Claude Code or Codex.

    cargo install --git https://github.com/JanSuthacheeva/flow --tag v0.1.0

Each worker starts with `/ship-feature <request>` (`$ship-feature` in
Codex), a skill from agent-skills that takes a feature from plan to merge
request. Install it and the skills it runs, or set your own first prompt
(see Configuration):

    npx skills add JanSuthacheeva/agent-skills --skill ship-feature
    npx skills add JanSuthacheeva/agent-skills --skill design-code
    ... implement-plan, review-changes, write-merge-request, commit

Then, in a repository:

    flow ui

The big pane is the master, an agent that works with flow for you. Ask it
to start a flow ("start a flow for SHOP-217 add CSV export"), or press
`C-space n`. Each worker shows up in the sidebar on the right, grouped by
what it needs from you. `C-space ?` lists every key.

On its first run flow writes `config.toml`, `theme.toml` and `master.md`
to `~/.config/flow`, every setting commented out at its default.

## What it does

- **Works with different agents.** Claude Code and Codex are built in,
  each followed through its own hooks. Any other command can run as a
  worker; flow then shows only whether it runs. The phases a flow walks
  through, the skills that start each phase and every agent's first
  prompt are settings.
- **Gives each worktree its own environment.** `.flow/setup` and
  `.flow/teardown` run in every worktree. `FLOW_SLOT` (1 to 20) is unique
  across all your projects, so each worktree's Docker stack can get its
  own ports. The `setup-flow` skill writes both scripts for your repo and
  tries them in a scratch worktree.
- **Has a master that is woken.** The master starts workers, answers them
  with `flow send` and is woken when one waits, is blocked or finishes.
  A guided flow asks you at every step; in an auto flow the master
  answers what the code and plan already settle.
- **Plain sessions.** An agent in any folder, without a worktree or a
  flow, next to your workers.
- **Themes.** Your terminal's colors by default, flow's own dark and
  light themes built in, reloaded while you edit. Another tool can write
  a theme for flow to follow (a Noctalia template is in the docs).
- **Sessions outlive the UI.** Closing the terminal leaves every agent
  running; after a reboot flow resumes each conversation.

## How it works

Every flow is an append-only log of events. The agents' own hooks run
`flow hook`, which turns what happens into events: a skill started a
phase, a question is waiting, a merge request was opened. flow folds the
logs into where each flow stands: its phase and how long each took,
tasks, blockers, decisions and a timeline. `flow server` runs each agent
in its own terminal and keeps it running; `flow ui` attaches to it.

## For agents and scripts

Every command answers in TOON, a compact format agents read well, with
the next steps beside it:

    $ flow status
    <real output with three flows>

Programs read `flow status --json`, a versioned contract. The command
line and the JSON are the only public interface; the logs are private.

| Command | Does |
| --- | --- |
| `flow` | every flow and what needs you |
| `flow ui [--stop]` | the terminal UI |
| `flow start <request>` | a worker in its own worktree |
| `flow start --plain <folder>` | an agent in a folder |
| `flow status [<flow>] [--json] [--all]` | where flows stand |
| `flow send <flow> <text>` | tell a worker something |
| `flow report <event>` | report into a flow by hand |
| `flow remove <flow>`, `flow clear` | tear down and forget |

Every flag is in docs/cli.md.

## Similar tools

Many tools run coding agents side by side in worktrees: Claude Squad,
ccmanager, dmux, amux, herdr, parallel-code and Conductor among them, and
several do things flow does not. Conductor, parallel-code and dmux have
diff review and pull requests built in; parallel-code reaches your phone;
herdr and ccmanager recognise many more agents. If you need one of those,
they will suit you better.

What flow does differently:

- It follows a feature, not only a session: phases, task counts,
  decisions, blockers and a timeline per flow.
- It learns what an agent does from the agent's own hooks instead of
  reading its screen.
- Its command line is made for agents, so a master agent can start,
  read and answer workers, and it is woken instead of polling.
- Each worktree gets its own setup, teardown and port slot.

Where flow falls short: it has no diff viewer or pull request button (the
worker's skill opens the merge request and flow notices it), no desktop
notifications, no phone access, and it follows only Claude Code and Codex.
It runs on macOS and Linux only.

# flow's settings. flow wrote this file on its first run; edit it freely,
# flow never overwrites it once you have. Every setting is shown commented
# out at its default: remove the leading # to change one.
# Reference: https://github.com/JanSuthacheeva/flow/blob/main/docs/configuration.md

#[worker]
# The agent `flow start` runs when it names none (--agent picks another).
#agent = "claude"
# The first prompt of every agent that sets none of its own, the built-in
# ones included. Unset: each keeps its own ("/ship-feature {request}" for
# claude, "$ship-feature {request}" for codex).
# For example: prompt = "/brainstorming {request}"

#[master]
# Wake the master when a worker waits, is blocked, goes idle or finishes.
#wake = true
# The agent the master runs. Unset: the built-in master (Claude Code).
# For example: agent = "codex"

#[ui]
# The key before every flow ui command: C-space, or C-a to C-z except
# the keys a pane needs (C-c, C-d, C-h, C-i, C-j, C-m, C-q, C-s, C-z).
#prefix = "C-space"

# The phases a flow walks through: 1 to 4, in order, each started by the
# skills it lists (with or without a plugin prefix). Yours replace these whole.
#[[phases]]
#name = "plan"
#skills = ["design-code"]
# ... implement, review, merge-request

Call chains

flow ui starts the server for the first time

  1. commands::server::run -> server::run(&ServerPaths { config, theme, .. }, ...)
  2. server::run -> write_defaults(paths, clock)
  3. write_defaults -> master::INSTRUCTIONS.ensure(&paths.instructions): Result<()>
  4. write_defaults -> config::EXAMPLE.ensure(path) when paths.config is Some
  5. write_defaults -> theme_file::EXAMPLE.ensure(path) when paths.theme is Some
  6. DefaultFile::ensure: file is text or not in earlier -> nothing; missing or an earlier default -> create_dir_all, fs::write(path, text)
  7. Error: an unreadable or unwritable file returns Err naming the path; write_defaults logs it to server.log and the server starts anyway, as master.md does today.

The config was already loaded before this (env.config()?), so the written file takes effect at the next command; it changes nothing anyway. The UI's theme watcher sees the new theme.toml within a second and reloads the same colors.

Conventions followed

  • First-run write and refresh: src/server/master.rs:30, now generalised, not copied.
  • Write failures logged, server goes on: src/server.rs:157.
  • Defaults stay in code (Config::default, Palette::TERMINAL); the examples are documentation the tests hold to them, never a second source loaded at runtime.
  • One responsibility per file: default_file.rs holds one struct; module is a noun (CLAUDE.md Structure).
  • Deviation: Serialize derives only under cfg(test), so production code gains nothing unused and dead code still warns.

Test seams

CHANGELOG draft

# Changelog

All notable changes to flow are listed here. The format follows
Keep a Changelog, and flow uses Semantic Versioning.

## [Unreleased]

The first public release, 0.1.0; the heading becomes
`## [0.1.0] - <date>` when it is tagged.

### Added
- flow ui: the master, every worker and plain session in one terminal,
  the sidebar, the peek, the board, the new-flow dialog.
- flow server: sessions outlive the UI and resume after a reboot.
- Claude Code and Codex workers, followed through their own hooks.
- Configurable workflow: 1 to 4 phases and the skills that start them.
- The master: starts and answers workers, woken by their news.
- Guided and auto flows, plain sessions.
- Per-worktree setup and teardown, FLOW_SLOT, branch conventions.
- Themes: terminal, flow, flow-light, live reload, extends.
- The command line for agents (TOON) and `flow status --json`.
- Commented example config.toml and theme.toml, written on first run.

### Known issues
- No desktop notifications; a waiting flow shows only in the sidebar
  and to the master.
- A Claude Code session interrupted with Esc keeps its spinner until
  its next prompt (Claude Code runs no hook on an interrupt).
- Codex flows show no task counts, and their flow is ended from flow ui
  or `flow remove`, since Codex has no exit event.
- Codex asks once to trust flow's hooks, again after they change.
- Background subagents are not counted; a worker running several looks
  merely working.
- The new-flow dialog starts flows in the repo of the session in view.
- macOS and Linux only.

CLAUDE.md rule: "Every PR adds a line under ## [Unreleased] in CHANGELOG.md (Added, Changed, Fixed, Removed), written for users. A release renames Unreleased to the version and date."

Assumptions

  • Only flow server writes the examples (first flow ui), not every command: hooks run flow constantly and should touch no files.
  • With FLOW_CONFIG set, the example goes to that path, and theme.toml beside it.
  • The demo repo is a tiny throwaway app in the scratchpad, not a real project; requests like "add CSV export". Recorded at 1600x900.
  • The README picture is a PNG; the GIF shows navigation (sidebar, peek, board) and sits below the quick start, not at the top.
  • docs/design/ and HANDOVER.md stay as they are, linked from nowhere public except CLAUDE.md.
  • The README's current reference tables (events, hook tables, JSON) move to docs unchanged in substance, rewritten in plainer words.
  • The help[] lines and error texts are documented as they read today; no CLI text changes in this branch.

Open questions

None left. Settled in review: no release date yet, everything stays under Unreleased until the tag; one skills line if npx skills add takes several --skill flags; the picture in flow's dark theme; phase_colors defaults to off and the picture shows it.
