Typing into a worker's pane

From a phone over remote control you cannot type /compact into a worker. flow send wakes the worker through its hook, so the model reads /compact as words and cannot run it. The server owns every pane's PTY: it should type a line and Enter into the pane once the worker is idle, as if you had typed it, and queue several lines in order.

What exists today

  • flow send appends Message { text } to the flow's log (cli/commands/send.rs:62) after refusing a worker as sender, empty text, an unknown, finished, worker-less or plain flow (send.rs:23-60). The worker's flow wait hands undelivered messages over and counts them in waits/<id>.delivered (deliver.rs:24).
  • For Codex, which cannot wake itself, the server pastes news into an idle pane: Server::deliver_news every 500 ms (server.rs:243, server/news.rs:22), only when waits/<id>.busy is absent and nobody typed into the pane for 10 s (news.rs:96). The bytes are one bracketed paste and \r (news.rs:102).
  • Only Codex marks .busy: Adapter::turn is None for Claude Code (adapter.rs:146), Codex maps UserPromptSubmit / Stop / Interrupt to Began / Ended / Interrupted (adapter/codex.rs:172), and flow hook sets and clears the marker (cli/commands/hook.rs:88).
  • A turn that flow wait wakes runs no UserPromptSubmit (HANDOVER.md, master row), and Claude Code runs no hook on an Esc interrupt (HANDOVER.md:304).

The same in every approach

  • Idle is reliable for both harnesses. Claude Code gets Adapter::turn too. Both map UserPromptSubmit and PreCompact to Began, Stop and PostCompact to Ended (Codex keeps Interrupt). A Claude Code Stop only clears the marker, its news stays flow wait's. flow wait marks the session busy when it wakes it with news, since that turn runs no prompt hook.
  • When a line is typed: the session had its first turn, is not busy, nobody typed into the pane for 10 s, and the line before it is done. The server marks the session busy as it types, so the next line waits for that turn's end.
  • A line that starts no turn (/cost, a typo) holds the queue at most 30 s, then counts as done.
  • Refused like flow send: from a worker, empty, unknown, finished, no worker, plain. Also a line with a newline: it is what you type before Enter.
  • Codex sees two new hooks (PreCompact, PostCompact), so it asks once to review flow's hooks again.
  • An Esc-interrupted Claude Code worker runs no hook, so it stays busy and a queued line waits until its next prompt.

A. The log holds the queue recommended

flow send --type appends a new Typed { text } event, like Message. The server keeps a count of the lines it typed per flow in waits/<id>.typed, next to .delivered, and types the next one when the pane is ready. The timeline shows master typed: /compact.

flow send --type->Typed { text }->flows/<id>.jsonl
flows/<id>.jsonl->Server::type_lines->Host::write (PTY)
flow hook / flow wait->waits/<id>.busy->Server::type_lines<->waits/<id>.typed

Gains

  • Mirrors Message and .delivered exactly: same refusals, same counting, same file layout.
  • Works without the server running: lines wait until flow ui opens the pane, and survive a server restart.
  • The record of what was typed into a worker is in its log and timeline.
  • No protocol change between UI and server.

Costs

  • One new event kind; an older binary folding the log skips it.
  • The command cannot say "typed": it answers "queued", the timeline shows when.

B. The server holds the queue

flow send --type connects to the server's socket with a new ClientMsg::Type { flow, text }. The server keeps the lines per pane in memory and types them as in A.

flow send --type->client->ClientMsg::Type->Server queue (memory)->Host::write

Gains

  • The command can refuse a flow whose pane is not open.
  • No new event or waits file.

Costs

  • Fails when no server runs; queued lines are lost when the server stops or restarts on an upgrade.
  • PROTOCOL_VERSION 6, and flow send needs a socket client next to its store write.
  • Nothing records what was typed.

Rejected: let the worker run it

Sending /compact as a message and telling the worker to compact itself does not work: a model cannot run a harness's slash command. Typing into the PTY is the only way short of the harnesses' own control APIs (Codex's codex queue refuses a session with -c overrides, HANDOVER.md).

The command

A public surface, so your call. Recommended: a flag on send, one line per call, calls queue in order:

flow send --type shop-217 /compact
flow send --type shop-217 "continue shipping"

Alternatives: a variadic flow send --type shop-217 /compact "continue shipping" (one call, one line per argument), or a separate verb flow type shop-217 /compact. The flag keeps one verb for "the master tells a worker", and the recommended form keeps <flow> <text> as send has it.

Recommendation

A, with flow send --type <flow> <line>. The log already is the queue for messages, and a queue that survives a server restart matters when you queue /compact and "continue shipping" from a phone and walk away.

Please pick A or B, and the command shape.
