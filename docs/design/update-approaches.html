design-code, step 2 of 3 - flow/update-notice - 2026-10-21

saaio update notice

Two choices shape the design: who asks for the latest release and how (the notice), and how saaio knows whether it is a release binary at all (the command). Signatures and call chains follow on the next page.

What exists today

  • No HTTP client in Cargo.toml. install.sh already needs curl, verifies the tarball against SHA256SUMS and replaces the binary by copy + rename, so a running server keeps its old file (install.sh:77).
  • Every release holds the four tarballs, SHA256SUMS and install.sh; a tag with - publishes a pre-release (release.yml:1, :178). The version check strips -rc.1, so an rc binary reports the plain Cargo version 0.1.1.
  • proto::BUILD is 0.1.0 (abc1234); nothing in the binary says whether CI built it or cargo install did (build.rs, src/proto.rs:18).
  • The UI loop already runs work off its thread and gets the answer back as an event (Event::Ran, src/ui.rs:270), and re-reads config.toml every second (reload_config).
  • The title row's right side shows a notice, else the rail hint when folded, else nothing (src/ui/app/chrome.rs:20).
  • Commands that need no store (bug-report, completions) dispatch before the store is opened (src/cli.rs:86). Processes with a deadline: workspace/process.rs.
  • saaio already reaches the network indirectly: the server runs gh and glab for merge requests. The docs line will say the update check is the one call saaio makes itself.

1. Who checks, and how

Recommended

A. The UI, on a thread, through curl, reading a VERSION asset

Each release gets one more asset, VERSION, holding its tag. The UI asks curl for releases/latest/download/VERSION (GitHub's "latest" skips pre-releases and drafts) with a 5 s limit on its own thread. The answer and the time go to update.json in the shared folder, so every project's UI on the machine shares one check a day and a restarted UI shows the notice without asking again. Offline, curl missing, a 404: nothing shows, nothing is logged.

newmodifiedexisting

Touches: new src/release.rs (versions, URLs, fetch), new src/update.rs (the daily check and its file), src/ui.rs, src/ui/app/chrome.rs, src/config.rs, release.yml (VERSION asset).

Gains

  • No new network stack: curl brings the system's TLS and proxy settings, as install.sh does.
  • The test fake is a file:// folder laid out like the releases page; curl reads it the same way.
  • No JSON, no API rate limit, no token.

Costs

  • A release asset more, and 0.1.0's release has none (harmless: only 0.1.1+ binaries ask, and they read the newest release).
  • Needs curl on PATH; without it there is no notice.
  • A UI that stays open for days needs an hourly look at whether the day passed.

B. The server checks and tells the UIs

The same fetch, run by saaio server, with a new ServerMsg::Update to every attached UI.

Gains

  • The server already runs background watchers (forge_watch).

Costs

  • A protocol change, and one server per project asks separately.
  • The UI owns the title row and its config already; the server would only relay.

C. An HTTP client in the binary, GitHub's API

ureq with rustls, reading api.github.com/repos/.../releases/latest JSON.

Gains

  • Works without curl; no release asset needed.

Costs

  • About 30 crates more to audit in cargo deny and a larger binary, for one request a day.
  • API rate limit (60/h per IP) and a fake needs an HTTP server in tests.
  • saaio update runs install.sh, which needs curl anyway.

2. Release binary or source build

Recommended

A. The release workflow stamps the tag into the build

release.yml builds with SAAIO_RELEASE=v0.1.1; build.rs passes it on like SAAIO_COMMIT. A binary without it was built from source: saaio update names the cargo install --locked --git ... --tag v0.1.2 --force line instead of replacing anything, and the notice still shows. The stamp is the exact tag, so an rc binary knows it is 0.1.1-rc.1, older than 0.1.1, and is told about the final release.

Gains

  • Certain: no guessing from paths.
  • Fixes the rc-reports-0.1.1 blind spot for comparisons.

Costs

  • One more build input; --version output stays as it is.

B. Guess from where the binary lives

Under ~/.cargo/bin or a target/ folder: source; anywhere else: release. Breaks for CARGO_HOME, a copied binary, or a release binary moved into ~/.cargo/bin, and replacing a source build with a release binary would silently switch the user's channel.

Recommendation

1A and 2A. They add no dependency, keep the check where the notice is drawn, make the fake a plain folder, and decide the source-build case from a fact instead of a path. saaio update then resolves the tag in Rust, checks the folder is writable, downloads that release's install.sh and runs it with SAAIO_VERSION and SAAIO_INSTALL_DIR set, so the checksum check and the rename stay in one place. Pick one per question, or say what to mix.
