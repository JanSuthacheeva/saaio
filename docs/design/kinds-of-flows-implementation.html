saaio 0.2.0 - design-code, phase 3 of 4 - 2026-10-28

Kinds of flows: implementation

1. Decision recap

Approach B: kinds live in config.toml as [kinds.<name>] with feature, fix and research built in, and saaio start records the kind's name, its whole workflow (phases and skills) and its first prompt in the flow's started line, so the server and saaio hook read the flow's own log and never config for a running flow.

  • Prompt: a kind has a skill and a prompt (default {skill} {request}); {skill} is /name for Claude Code, $name for Codex, bare otherwise. An agent's own prompt still wins; [worker] prompt is the feature kind's.
  • Branch type: a kind lists the types it means; the first one the repo lists wins, else the repo's first. --type overrides.
  • Research: branch = false, a worktree detached at the base, one phase research; done once it answers, and saaio clear forgets it then (section 9).
  • Old configs: top-level [[phases]] is the feature kind's; with [[kinds.feature.phases]] too it is an error on its line. [worker] kind picks the default, feature.
  • Shown: the kind in saaio status (list and detail), --json, the board's detail and the sidebar. master.md tells the master to pick it: a bug report or bug ticket is fix, a question to answer is research, anything else feature, always passed as --kind.

3. Units

src/kind.rs new

What a kind of flow is: its workflow, how it is started, and whether it gets a branch.

/// The kind a flow runs when none is named and [worker] kind is unset.
pub const DEFAULT_KIND: &str = "feature";

/// One [kinds.<name>]: the workflow, the skill and prompt that start it, its branch.
#[derive(Debug, Clone, PartialEq, Eq, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct Kind {
    pub phases: Workflow,
    /// The umbrella skill the first prompt runs: ship-feature, ship-fix.
    #[serde(default)]
    pub skill: Option<String>,
    /// The first prompt; None is "{skill} {request}", or "{request}" without a skill.
    #[serde(default)]
    pub prompt: Option<String>,
    /// The branch types it means, in order of preference.
    #[serde(default)]
    pub branch_types: Vec<String>,
    /// false: a worktree detached at the base, no branch (research).
    #[serde(default = "with_branch")]
    pub branch: bool,
}

impl Kind {
    /// feature, fix and research.
    pub fn builtins() -> BTreeMap<String, Kind>;
    /// The built-in feature kind, for flows recorded before kinds.
    pub fn feature() -> Kind;
    /// The first prompt template for `agent`: its own prompt, else this kind's, else the
    /// default, {skill} filled in as the agent's harness calls a skill; {request}, {id} and
    /// {name} stay for the pane to fill.
    pub fn prompt_for(&self, agent: &Agent) -> String;
}

Built-ins:

feature  skill ship-feature  branch_types [feature, feat]
         plan design-code, implement implement-plan, review review-changes,
         merge-request write-merge-request
fix      skill ship-fix      branch_types [fix, bugfix, hotfix]
         diagnose diagnose-bug, implement implement-plan, review review-changes,
         merge-request write-merge-request
research branch = false
         prompt "Research this and answer here. Change no code and commit nothing: {request}"
         research (no skills)

6. Conventions followed

  • Config::kind and worker_kinds mirror Config::agent and worker_agents (config.rs:241, config.rs:226); built-ins under the file's, as add_builtins does for agents (config.rs:196).
  • A built-in name replaces the built-in whole, as for agents (examples/config.toml, "An agent with a built-in name replaces the built-in one").
  • Old config shapes refused with a message on their line, as parse does for [phases] (config.rs:175).
  • Optional started fields with skip_serializing_if and old lines read back, as phases (event.rs:39, test event.rs:842).
  • pick_kind failures list what exists, as pick_agent (start.rs:160).
  • Dialog rows cycle like the agent and type rows (newflow.rs:37); Job::args adds a flag only when it is not the default (effect.rs:52).
  • master.md change with the previous text kept as master-v13.md (master.rs:24).
  • Example file lists every built-in, so the test that compares examples/config.toml with the built-ins fails until it does.
  • Deviation: the started line's field is flow_kind, not kind, because kind is the event's tag.

8. Assumptions

  1. Fix's phase names are diagnose, implement, review, merge-request; the phase colors follow position, so they look like feature's.
  2. saaio new takes --kind too, so a tracked flow shows the right steps.
  3. A user kind must name its phases; a built-in name replaces it whole, no field-wise merge.
  4. Old flows show no kind (null in --json, nothing in the sidebar); they are not relabelled feature.
  5. An old flow never opened before the upgrade gets the built-in feature prompt for its agent, ignoring [worker] prompt.
  6. The sidebar shows the kind only when it is not feature, so the common case stays as it looks today.
  7. Research keeps a slot and runs the setup hook, so it can run the project.
  8. The dialog's kind row is shown always (three built-ins), right below the request.

9. Decided in review

  1. flow_kind is the key in the started line.
  2. A research flow finishes by answering. The kind's branch = false is recorded as "merges":false in started. In such a flow, a turn that ends without a question folds to done instead of idle (timeline "answered"); a later turn makes it working again, as a done feature flow can. Being done gives it what a done feature flow has: the DONE group in the sidebar, its services paused after pause_after_minutes, the master told it is ready. On top, saaio clear takes a done flow that merges nothing (FlowView::is_clearable): it closes its pane, runs teardown, removes its worktree (kept with uncommitted work) and forgets it, which releases its slot. A feature flow still needs its session ended first, as today, since it may still have review or merge work.
