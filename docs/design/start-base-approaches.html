saaio 0.2.0 - design-code, step 1 of 2 - branch flow/start-base

Stacked flows with saaio start --base

Every approach shares the same front half: --base <branch> on saaio start, a base row in the new-flow dialog, the base recorded with the flow, shown in status and --json, and told to the worker so its merge request targets the base. They differ in one thing: what happens when the base merges first.

What exists today

  • saaio start builds the branch name, then git worktree add -b <branch> <path> with no start point, so the worktree starts at the main checkout's HEAD (src/launch/worktree.rs:32, src/cli/commands/start.rs:102).
  • Where a flow runs is the Workspace event: path, branch, slot, window, agent (src/event.rs:116). The server re-appends it with window: saaio-ui when it opens the pane, copying every other field (src/server/panes.rs:202), so a new field there survives.
  • The worker knows nothing of its target: its instructions are the fixed WORKER_PROMPT (src/adapter.rs:22) and the hooks' env SAAIO_FLOW_ID/NAME/SLOT/WORKTREE/REPO (src/launch/worktree.rs:89). The skill opening the MR picks the default branch.
  • The server asks gh/glab about each flow's branch every two minutes and appends merged once its MR merged (src/forge.rs:293, src/server/forge_watch.rs).
  • A worker hears only the master's messages: Message events not yet delivered (src/wake.rs:22). The master is woken only when a flow stops, not when one merges.
  • --json may gain keys without a new version (docs/json.md, Versions).

Shared by all approaches

  • Another flow's branch as base: any local branch is a start point, also one checked out in another worktree. The base's latest commits are taken at start; the base must be on the remote before the stacked flow pushes, which the worker prompt says.
  • Remote-only base: not a local branch but <remote>/<base> exists (after a git fetch): start from that ref, with --no-track, so the flow's branch does not pull from or push to the base.
  • Unknown base: refused before anything is created, like an unknown agent.
  • The worker gets SAAIO_BASE and one more sentence in its instructions: open the merge request against <base>, rebase on it, not on the default branch.
  • Status: saaio status <name> and the board's detail show base; --json adds workspace.base (null without one).

A. Record the base, the master keeps the stack smallest

saaio records the base and nothing more. When a base merges, the master (which usually merges on the user's OK) tells the flows stacked on it to rebase and retarget; master.md gets the rule. A merge on the forge's web page goes unnoticed until someone looks.

Least code, nothing new in the server. Keeps judgment with the master, as for every other coordination.
Depends on the master noticing the merge. After a squash merge the stacked branch still carries the base's old commits until someone rebases; status keeps showing a base that no longer exists.

B. saaio follows the stack recommended

As A, plus: when the server sees a flow merge (the forge answer it already appends), every unfinished flow whose base is that branch gets a base-merged event naming the new base (the merged flow's own base, else the default branch). The fold moves base to it, and the worker hears it as news, like a master message: rebase onto the new base, retarget the MR, push. The master hears it in its next wake list.

Touches everything in A, plus a small pure stack.rs (which flows a merge affects, what their new base is), server/forge_watch.rs, wake.rs, fold.rs.

Works whoever merges and wherever. Status is never stale. The rebase still happens in the worker, which owns its worktree and can resolve conflicts.
One more event kind and one server reaction. Only bases that are flows in the same store are followed; a base branch nobody runs as a flow stays as A.

C. saaio rebases the stack itself rejected

The server runs git rebase --onto in each stacked worktree and retargets the MR through gh/glab.

Rejected: the server would run git in a worktree whose .git and hooks the worker controls, which saaio avoids on purpose (src/workspace/git.rs:166); a conflict needs an agent anyway; it races a working worker.

Recommendation

B. A stack is exactly the case where one merge silently breaks the next flow: its MR points at a merged branch, and after a squash it shows the base's commits again. saaio already learns of every merge; acting on it costs one pure module and one event, and keeps the rebase where it belongs, in the worker. GitHub and GitLab retarget an MR themselves only when the merged branch is deleted, so the worker's retarget is still needed.

Which one, A or B? Questions on the dialog field and on fetching come with the implementation page.
