design-code / phase 2 - pick an approach

The master and its workers talk to each other

Three pieces, designed together: the master can send a worker an instruction or answer; the master is woken when a worker finishes, gets blocked or asks something; and the master can read a worker's result. The approaches differ in how a message reaches a session that is sitting idle at its prompt.

new modified unchanged

What exists today

  • Workers report through Claude Code hooks: Adapter::wiring adds --settings with a flow hook claude-code handler on each event (src/adapter/mod.rs:36, src/adapter/claude_code.rs:25), and the fold turns them into working, delegated, waiting, idle, blocked (src/event.rs:18).
  • The master gets no hooks and no FLOW_ID: MasterRecord::spec builds its argv with pane_env(None, ..) (src/server/master.rs:76). It learns about workers only when it runs flow status, which master.md tells it to do before saying anything.
  • Nothing can put text into another session except you typing into its pane. The server owns every PTY (Host::write, src/server/host.rs:118), but only the attached UI's keys go there.
  • A worker's result is visible only as the last 200 characters of its turn (Waiting{question}, Idle{note}) and the timeline in flow status <name>. The full last message is in the Claude transcript, which only the UI's peek reads (src/ui/peek.rs:39).
  • Verified today on Claude Code 2.1.300: a Stop hook with "asyncRewake": true runs in the background, and when it exits with code 2 its output wakes the idle session as a new turn (shown to you as "Stop hook feedback"). A probe with a 25-second sleep woke an idle Haiku session at its prompt, and the hook is armed again at each turn end.

A. Messages in the log, delivered by the agent's own hooks recommended

flow send <flow> "<text>" appends a Message event to that flow's log, like any report. Every session, the master included, gets one more hook: an asyncRewake Stop handler, flow wait, that sleeps until there is news for that session, prints it and exits 2. Claude Code then wakes the session with the news as its next turn. For a worker the news is a message for it; for the master it is a worker that became waiting, blocked, idle or done, or a message a worker sent the master.

Fits

  • Same path as every other report: a command appends an event, the fold reads it (CLAUDE.md "Data flow"). The conversation is in the record: flow status <name> shows it in the timeline.
  • Works with or without flow ui running; the server does not change.
  • The message arrives as hook feedback, not as if you typed it, so a worker can tell "the master says" from "the user says".
  • Only a sleeping session is woken; a working one gets the news at its next turn end, without breaking into what it is doing.
  • Testable without a terminal: flow wait is a command with a log in, text and exit code out.

Costs

  • Relies on asyncRewake, a Claude Code hook option. Another agent in config.toml gets no channel until its adapter has an equivalent (Claude Code is the only adapter today).
  • One sleeping flow wait per session. Each turn end arms a new one, so a newer waiter has to replace the older (a lock per session).
  • The master's waiter must not miss a change that happens between its turn end and the waiter starting, so the master keeps a "seen" mark in the store.
  • New event kind in the log format: older flow binaries reading a newer log would fail on it (we always install both together).

Touches: event.rs (Message), fold.rs/view.rs (messages in the timeline, a flow's result), main.rs (send, wait), adapter/claude_code.rs (the wait hook), server/master.rs (master hooks and env), output.rs, master.md.

B. The server types into the panes

flow send connects to the server (a Control connection, like flow remove) and the server writes the text and Enter into the target pane's PTY, as if you had typed it. The server also watches the board and types a summary into the master's pane when a worker needs it.

Fits

  • Works for any agent with a prompt, not only Claude Code.
  • No sleeping processes; the server already owns every PTY.

Costs

  • Collides with you: if you have half a sentence typed in that pane, the message is appended to it and both are sent.
  • The worker sees the message as your words; it cannot tell the master from you.
  • Each agent's input box differs (paste detection, vim mode, / and ! prefixes, multi-line). Typing reliably is guesswork per agent and version.
  • Only works while flow ui's server runs, and the master still needs hooks to know when it is idle, so it does not save the master wiring.
  • Nothing lands in the log, so flow status cannot show the conversation.

C. An MCP channel rejected

flow would run an MCP server that declares Claude Code's claude/channel capability and pushes messages into each session. The 2.1.300 binary describes channels as gated: a server is only offered when its plugin is on an approved allowlist (or the session starts with a development flag), and claude.ai Team and Enterprise accounts have them off by default. A flow every worker depends on cannot rest on a research preview your organisation may switch off.

Second decision: who answers a waiting worker?

This decides what wakes the master and what master.md tells it, not the structure, so it applies to whichever approach you pick. Your rule so far: "needs you" should only mean a decision is yours.

1. The master first

The master answers what the code, the plan or your earlier decisions settle, sends the answer with flow send, and tells you what it answered. Product decisions stay with you. Fewest interruptions; the master decides some things for you.

2. You, the master relays

The master never answers on its own. It tells you which worker asks what, with what it found in the code, and sends your answer when you give it to the master. Safest; you are interrupted as often as today.

3. By the flow's mode recommended

The mode already says how much a flow may do alone: an auto flow's questions go to the master first (1), a guided flow's go to you with the master relaying (2). No new setting; you choose per flow when you start it.

Recommendation

A with answer rule 3. A puts the conversation where everything else about a flow already lives, never types over you, and lets a worker tell the master's words from yours. Its one real cost, depending on asyncRewake, is the same kind of dependency flow already has on Claude Code's hooks, and today's probe shows it works on your version. B's collisions with your typing are the sort of thing that makes you stop trusting the tool.
