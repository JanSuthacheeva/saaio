flow 0.1.0 release docs

Three choices shape the rest: how the commented example files reach a new user, how they are commented so a test can prove them, and how the README picture is made. The README draft and the docs outline follow on the next page, once these are settled.

What exists today

  • README.md (~470 lines) is the whole manual: commands, events, keys, themes, agents, hooks, workflow, master, the JSON contract, where logs live. docs/ holds only HANDOVER.md and design pages.
  • config.toml is optional: no file means the built-in agents, workflow, [worker], [master] and [ui] defaults (src/config.rs:93). Unknown keys are errors (deny_unknown_fields).
  • theme.toml is optional too: no file means the terminal theme (src/ui/theme_file.rs:47), whose colors are ANSI names like Blue and DarkGray (src/ui/theme.rs:49). A theme file can only write "#rrggbb", an index 0-255, "default" or another key (theme_file.rs:262), so Blue is today not writable as itself: index 4 parses to Indexed(4), not Blue.
  • flow already writes one file on first run: master.md beside config.toml. ensure_instructions writes it when missing and replaces it when it still holds an earlier default, never when edited (src/server/master.rs:30, earlier defaults in master-v1.md to -v7.md).
  • The default first prompt is /ship-feature {request}, from the public agent-skills repo, which also has setup-flow and the npx skills add install lines.
  • No vhs or asciinema installed; ffmpeg is.

1. How the example files reach a new user

Recommended

A. flow writes them on first run, like master.md

The examples live in the repo (examples/config.toml, examples/theme.toml) and are compiled in with include_str!. When flow ui starts and finds no config.toml or theme.toml, it writes the example there. Every setting in them is commented out, so the written file changes nothing. The master.md logic becomes one small shared unit, so an untouched example is refreshed by a newer flow and an edited one is never touched.

newmodified

Touches: src/server/master.rs (its write logic moves), a new src/default_file.rs, the server start where ensure_instructions is called, examples/.

Gains

  • Found where people look: the file is just there, as Hyprland does.
  • Follows the one first-run write flow already has, and makes it shared instead of a second copy.
  • Untouched files stay current across releases.

Costs

  • Writes into ~/.config/flow without asking (as master.md already does).
  • Each future change to an example keeps the old text as config-vN.toml for the refresh check.
  • An edited file stops getting new comments; the docs and examples/ stay the reference.

B. A command prints them

flow example config and flow example theme print the current text; the user redirects it into place. The README and the docs point to the command. Nothing is written unasked.

Gains

  • Never writes files; always matches the installed version.
  • Works to diff an edited file against the current example.

Costs

  • A new command in the public surface, kept forever.
  • Only found by reading docs.

C. Both

A, plus the command from B for people who edited their file and want the current one to compare. Largest surface; I would add the command later if anyone asks for it.

2. How the examples are commented

Recommended

Settings commented out at their default, sshd_config style

# The agent flow start runs when it names none.
#agent = "claude"

# The first prompt of every agent that sets none. Unset: each keeps its own.
# For example: prompt = "/brainstorming {request}"

#key = value (no space) is a setting at its default; # text is explanation. A key with no default ([worker] prompt, [master] agent) appears only in an explanation line. The test uncomments every #key line and checks two things: the result parses to exactly the built-in defaults, and no setting is missing (for config.toml by comparing with the built-in config written out as TOML; for theme.toml against every color key the code knows).

The alternative, live values like Hyprland's file, pins today's defaults into every user's file: when a default changes later, users who edited one line keep the old value for every other key. Commented settings keep following flow.

One code change this needs: index 0-15 in a theme should mean the terminal's named colors (4 is Blue), so the terminal theme can be written in its own file. It renders the same; today 4 sends the 256-color code for the same palette entry.

3. The README picture

Recommended

A VHS tape in the repo, run against real workers in a scratch store

docs/media/demo.tape (VHS, installed with brew) opens flow ui with a scratch FLOW_HOME on a small sample repo, starts three or four real Claude Code workers, waits until they sit in different states (planning, waiting for you, implementing, done), and takes a PNG screenshot plus a short GIF: sidebar, a peek, the board. The tape makes it repeatable for the next release; the agents' text will differ each run.

Gains

  • Real sessions, nothing staged.
  • Regenerate after a UI change with one command.

Costs

  • A few dollars of tokens per take, and some retakes until the states line up.
  • Needs vhs (with ttyd) installed.

Alternatives: a scripted fake agent that prints a session and calls flow report (exactly repeatable, but staged, which does not fit the tone); or a hand-taken screenshot only (cheapest, not repeatable).

My recommendation

1A, 2 as shown, 3 with VHS. It reuses the one first-run write flow already has instead of adding a second mechanism or a new command, the tests prove the examples stay true, and the picture shows real work.
