design-code / phase 2 - pick an approach

flow ui follows the Noctalia theme, live

Decided: flow ui can follow Noctalia, and you can also pick the colors of the TUI design. When Noctalia switches theme, flow ui repaints in the new colors without a restart; without a theme it looks as it does today. The three approaches differ in where flow gets the colors from and how it notices a change.

What exists today

  • Theme::builtin() (src/ui/theme.rs:61) is the only theme: tokens ui.{text, strong, muted, faint, accent, rule, selection, key, bar} and state.{working, waiting, blocked, done, ended}. It is built once in main::ui (src/main.rs:373) and handed to ui::run, which passes &Theme to every draw.
  • Most tokens are ANSI 0-15, so they already follow the terminal's palette, which Noctalia sets through your terminal-sequences template. Four colors are fixed: the clay accent (256-color 173), the bar (235 on 252) and the selection (236). Those are what clash with a Noctalia theme. The board's solid pills also hard-code black text (src/ui/board.rs:321).
  • Noctalia renders user templates on every theme change: [theme.templates.user.*] with input_path, output_path and an optional post_hook (dotfiles-v2/noctalia/theme.toml:16). Your nvim template reloads nvim with pkill -SIGUSR1 nvim. tmux gets @noctalia_* options from the community tmux template.
  • Noctalia runs on your Linux machine. On this Mac, ~/.config/tmux/themes/noctalia.conf is a static copy from Sep 22, so "live" only happens where Noctalia runs; elsewhere the file stays as it was written.
  • The design canvas already has a Theme artboard: ~/.config/flow/theme.toml with extends = "terminal", sections [ui] (background, panel, selection, rule, text, strong, muted, faint, accent), [state] and [glyphs]; a color is "#rrggbb", an ANSI index 0-15, "default" or another key; a key left out keeps the built-in value; "flow reloads the theme when the file is saved". Its other artboards use a dark palette (ground #141418, text #c8c8d0, clay #e07a52, blue #7aa7ff, amber #e5b45a, red #f0717f, green #93c46d); the Theme artboard shows a light one.
  • flow ui already ticks every 100 ms (src/ui/mod.rs), and the server notices changes from file sizes and times (src/server/watch.rs).

A. A theme file in flow's own token names, watched by flow ui recommended

The design's file: ~/.config/flow/theme.toml picks a base with extends and overrides any key. Bases are built in (terminal: today's look; flow: the design's dark palette; flow-light: its light one) or files in ~/.config/flow/themes/. A Noctalia user template in dotfiles-v2 writes themes/noctalia.toml on every theme change, mapping Material roles to flow's keys; extends = "noctalia" follows it, extends = "flow" gives the design's colors, and switching is one line. flow ui checks both files' size and time once a second and swaps the theme when either changes.

Gains
  • Exactly the file the design already shows, and the design's palette as a built-in theme.
  • flow knows nothing about Noctalia: any tool, or you by hand, can write the file. Codex or another shell later is just another template.
  • The mapping lives in the template, where you can change it without a flow release.
  • Notices every change, including a hand edit or a theme written while flow ui was closed.
  • Fits flow's habits: a file under ~/.config/flow like config.toml, change detection from size and time like StoreWatch.
Costs
  • One stat per second while flow ui runs (negligible).
  • A repaint can lag a theme change by up to a second.
  • A theme file format to keep compatible from now on: token names become public.

B. Same file, reloaded on a signal from Noctalia's post hook

As A (same files and built-in themes), but the template's post_hook sends flow ui a signal (like your nvim template does), and flow ui reloads the file only then.

Gains
  • Repaints the moment the theme changes; no polling.
Costs
  • pkill -USR1 flow also hits flow server and every flow hook, and SIGUSR1's default is to terminate: one theme change could kill every Claude session. The hook needs an exact pattern for flow ui only, and every flow process must ignore the signal.
  • Misses a hand edit, or a theme written while flow ui was closed until the next start.
  • The template has to know how to find flow's processes.

C. No template: read the colors tmux already has

flow ui asks the tmux server for the @noctalia_* options (tmux show-options -gv) and maps the Material roles to its tokens in Rust, polling every few seconds.

Gains
  • Nothing to add to dotfiles-v2; works wherever tmux has the palette.
  • The design's palette can still be a built-in theme.
Costs
  • Leaves the design's theme file out, or needs it as a second mechanism.
  • Ties flow to tmux and to the names the community tmux template happens to set; outside tmux, no theme.
  • The role-to-token mapping is compiled into flow.
  • Spawns a process on every poll.

Recommendation: A

A keeps flow independent of Noctalia and tmux, puts the mapping where you can tune it, and cannot harm the sessions. B's speedup is under a second, and its signal would have to be fenced off from the server and every hook. C couples flow to tmux.
