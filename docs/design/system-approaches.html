design-code / phase 2 - pick an approach (round 2)

Where does the flow system live: files, a daemon, or a CLI that drives everything?

Since round 1 the scope grew: a Rust CLI flow so it works across harnesses, a progress view (history, not just the current state), and an auto mode where small features run to the MR without stops. The decision here is the structure: what holds the flow state, who writes it, and who decides the order of phases. Names and formats come on the implementation page.

new modified unchanged

What exists today, and what is decided

  • agent-skills: design-code, implement-plan, review-changes, write-merge-request, agent-agnostic, each usable alone; ship-feature (designed as if it exists) runs them in order and stops for approach, plan approval, a blocked build, open review items, push + MR.
  • The skills already sort every decision into cheap to reverse (decide, note it) and expensive (stop and ask) - design-code/SKILL.md phase 1, implement-plan/SKILL.md section 3. Auto mode builds on exactly that split.
  • plan-progress mod: report tool, store, 2 s file poll, pure model + drawing - the template for the viewer.
  • A mod can observe a worker on its own: skill.prompt, tool.call (Agent, AskUserQuestion, plan-progress, Bash), turn.start / turn.complete.
  • A mod can read and list files at any absolute path ($.fs) and run processes ($.process.run).
  • claude -w <name> --session-id <uuid> -n <name> creates the worktree and names the session.
  • Decided: workers are separate sessions started by the master; you answer blockers in the worker; status comes from observation in Claude Code, not from the model remembering to report.

The state is an append-only event log per flow (started, phase entered, decision made, task done, blocked, answered, review items, MR opened, ended). The board derives the current state, phase durations, task bar and timeline from it; nothing is overwritten, so progress and "what happened while I was away" come for free.

Auto mode lives in the skills

  • ship-feature takes a mode (auto or guided); in auto, design-code picks its recommended approach and writes the plan without review pages, recording every choice under ## Decisions.
  • Guardrail: anything expensive to reverse (stored data, public surface, user-visible behaviour) stops the flow even in auto. Cheap decisions never do.
  • write-merge-request leads with the decisions, so the one review at the end covers code and choices.
  • Costs: a non-interactive path in design-code and ship-feature, and evals that prove auto picks sensibly and really stops on the expensive cases.

A. flow CLI owns event files; the mod adapts and views

recommended

The Rust CLI is the only writer: flow start creates the worktree and launches the worker from a per-harness command template, flow report appends one event to ~/.local/state/flow/<id>.jsonl, flow status prints a board. In Claude Code the mod observes the worker and calls flow report; in other harnesses the skills report through one optional line ("if a flow command exists, report each phase and decision"). The master's mod lists and reads the files and draws the board.

Touches

New repo flow (Rust); new mod flows/; modified agent-skills: ship-feature (mode), design-code (non-interactive path), write-merge-request (decisions first), one optional report line.

Gains

  • Harness-agnostic: files and a shell command are the whole contract.
  • Append-only, one writer per file: no locking, no lost updates, history for free.
  • Works with nothing running: no daemon, the board is just a reader; flow status works without the mod.
  • Mod stays thin and testable with a fake process and fake files.

Costs

  • A binary to build and ship (cargo, brew); the mod must explain when it is missing.
  • The event format is a contract between two repos: versioned from day one.
  • Polling files every 2 s, not a push; one process start per report.
  • Other harnesses rely on the model calling flow report.

B. flow serve daemon holds the state

Same CLI surface, but flow serve runs in the background and owns the state in memory (persisted to SQLite); flow report and the mod talk to it over a local socket or HTTP. The board can get pushed updates instead of polling.

Touches

As A, plus a server, a protocol, and daemon start/stop handling in the CLI and the mod.

Gains

  • Instant updates, queries over many flows (e.g. "all flows this week").
  • One place to enforce rules (single writer by construction).

Costs

  • A process that must be running: who starts it, what if it died, ports and sockets.
  • Not verified: whether the mod's $.http may reach localhost.
  • Much more code for a board that refreshes every 2 s just fine.

C. flow drives the phases itself

The CLI replaces ship-feature: flow run SHOP-217 --auto runs each phase as its own harness session (design-code, then implement-plan, review-changes, write-merge-request), reads the plan and review files between them, applies auto mode and the stops itself, and writes the event log as in A. The skills stay unchanged and agent-agnostic; the mod only views.

Touches

New repo flow with the orchestration; new mod flows/ (viewer); ship-feature is not written; design-code still needs its non-interactive path for auto.

Gains

  • Deterministic order and stops: code, not instructions, decides when to stop.
  • Status is exact - the CLI knows the phase because it started it; no observation needed.

Costs

  • Each phase starts cold: design discussion and context do not carry into the build (by design for review, a loss for the rest).
  • Driving interactive sessions from a CLI per harness is the hard part (headless runs cannot ask you).
  • Throws away the approved ship-feature plan; judgement moves out of the agent.

Recommendation: A

Files plus a shell command is the smallest contract that works for every harness, append-only logs give the progress view and history without a database, and nothing has to be running for the board or flow status to work. ship-feature keeps the judgement about phases and auto mode, as already approved. B can come later behind the same CLI if push updates or cross-flow queries become worth a daemon; C is the fallback if instructions prove unreliable at keeping the order and stops.
