1. Decision recap

Approach A: the flows mod gains a reporter. A pure reporter.ts maps each Claude Code event to the arguments of one flow report call; register.tsx hooks the events and runs the calls in order. It does nothing unless the session has a flow id (FLOW_ID).

Just an adapter (your note): the mod keeps no flow state and makes no flow decisions. It only translates what Claude Code shows into flow's agent-neutral events (phase, working, delegated, waiting, blocked, tasks, merge-request, ended, heartbeat); flow folds them, as it would for any other harness. The only Claude Code knowledge lives in reporter.ts, and the one piece of in-session bookkeeping is a counter of running subagents, so a subagent's turn does not read as the worker's.

4. Data

Observation crosses hooks -> reporter.ts and is never stored. The output crosses the process boundary as flow report argv; nothing new is stored by the mod.

5. Call chains

5.1 A phase skill starts

  1. skill.prompt { skill: 'design-code' } -> observe($, { kind: 'skill', skill }) -> return next(e)
  2. flowId null -> observe returns; nothing runs
  3. reporter.reportArgs(observation): ['phase', 'design'] -> enqueueReport($, args)
  4. reportQueue = reportQueue.then(() => runReport($, args)) -> $.process.run([flowPath, 'report', '--flow', flowId, ...args], { timeoutMs: 5_000 })
  5. rejects or exit != 0 -> !hasWarned: $.ui.toast('flows: could not report to flow - <first line>'), hasWarned = true; the queue goes on

5.2 A subagent runs (implement-plan in a fresh agent)

  1. tool.call Agent { description, run_in_background } -> background: return next(e) unobserved
  2. runningAgents++ -> observe({ kind: 'delegated', description }) -> 'delegated "implement plan"'
  3. result = await next(e) (the subagent's own turn.start / skill.prompt fire meanwhile: turn-start is skipped while runningAgents > 0; its skill.prompt still reports the phase)
  4. finally runningAgents-- -> observe({ kind: 'agent-done' }) -> 'working' -> return result
  5. next(e) throws -> the finally still runs; the error passes on unchanged

5.3 Waiting: a question, or the turn ends

  1. tool.call AskUserQuestion { questions } -> observe question(questions[0].question) -> 'waiting "Which approach...?"'; result = await next(e); observe answered -> 'working'
  2. turn.complete { answer, agentId: undefined } -> observe turn-end -> reporter.waitingQuestion(answer) -> 'waiting "Approve the implementation page?"'
  3. turn.complete with an agentId -> ignored (a subagent's turn)
  4. turn.start (the person answers) -> observe turn-start -> 'working'

5.4 plan-progress reports and the MR

  1. tool.call mcp__plan-progress__report -> result = await next(e) -> denied: nothing; else observe plan-report { status, item, note, result: text of the result }
  2. status blocked -> 'blocked "5: migration needs a default"'; doing / done -> reporter.taskCounts(result) -> 'tasks 4 9'
  3. tool.call Bash -> result = await next(e) -> observe command { command, stdout } -> reporter.createdMergeRequest(command, stdout) -> 'merge-request https://gitlab.com/.../88'
  4. no URL in stdout (the create failed) -> nothing

5.6 /flows join shop-221

  1. command.run { args: 'join shop-221' } -> joinFlow($, 'shop-221')
  2. $.process.run([flowPath, 'status', 'shop-221', '--json']) -> parseBoard(stdout) -> board.flows[0].id
  3. exit != 0, unparsable or empty -> answer 'No flow named shop-221.'; flow missing -> the install hint
  4. flowId = id -> observe({ kind: 'turn-start' }) -> 'working' -> answer 'Reporting to shop-221.'
  5. /flows join with no name -> answer 'Usage: /flows join <name>'

5.5 Start, heartbeat, end

  1. session.start -> flowId = (await $.env.get('FLOW_ID'))?.trim() || null
  2. clock.every(30_000) -> observe heartbeat -> 'heartbeat'
  3. session.end { reason } -> reason 'clear' -> nothing (same worker, new conversation); else 'ended', and the queue is awaited before next(e)

6. Conventions followed

  • Pure mapping module + hooks in register.tsx: flows/hooks/board.ts / register.tsx.
  • Tool hooks that act after await next(e) and pass the result on: plan-progress/hooks/register.tsx (report tool), merge-status's git trigger.
  • MR creation pattern: merge-status/hooks/git.ts:17 ((glab mr|gh pr) (create|new)).
  • $.env.get for host variables: merge-status/hooks/register.tsx:56; processes with a timeout through one path: flows/hooks/register.tsx (readBoard).
  • Every hook ends in .catch(($, e, next) => next(e)), except tool hooks after their next(e) ran: there observe never throws, so next never runs twice.

7. Test seams

  • reporter.ts - unit: every row of the mapping, prefixed skill names, waiting question (last line, cut, empty), task counts ("4/9 done", "all 9 done", none), MR detection (gh, glab, other commands, no URL).
  • register.test.tsx - engine tests with a fake flow recording argv and mock.env for FLOW_ID: nothing without a flow id; a skill, an Agent call (and background skipped), AskUserQuestion, a plan-progress report, a Bash MR, a main and a subagent turn.complete, heartbeat, session end (clear and not) produce the expected calls in order; a failing flow toasts once.
  • End to end: a real Claude session with FLOW_ID of a flow made by flow new, asked to run /design-code on a tiny change; flow status and the board show the phases and waits as they happen.

8. Assumptions

  1. The four phase skills are matched by name, also with a plugin prefix; any other skill reports nothing.
  2. Background subagents (run_in_background) are not reported as delegated.
  3. The waiting question is the last non-empty line of Claude's answer, cut to 200 characters.
  4. Task counts come from plan-progress's result text ("4/9 done"); a format change there silently stops them (both live in this repo, covered by a test here).
  5. Heartbeat every 30 s; flow marks a worker not responding after 90 s without one.
  6. A failing flow shows one toast per session, then reports are dropped quietly so the worker is never disturbed.
  7. Reports run in event order through one queue; the session end waits for it.
  8. /clear is not an end; the worker keeps its flow id.

9. Decided in review

  • Turn ends: every end of Claude's main turn reports waiting with the answer's last line.
  • Becoming a worker: FLOW_ID at start, or /flows join <name> in a running session (chain 5.6). join is a reserved word, not a flow name.
  • Decisions: not from the adapter; piece 6 reports them from the skills.
