design-code / phase 2 - pick an approach

One flow per project: how does a slot stay unique across projects?

Decided already: stores register themselves in a shared folder (~/.local/state/flow), there are 20 slots across all projects, and the overview lives in flow status --all and flow ui. All three approaches share the registry and the overview; they differ in how flow start takes a slot so two projects, or two starts in one project, never get the same one.

new modified unchanged

What exists today

  • launch::free_slot(flows) returns the lowest of MAX_SLOTS = 9 that no unfinished flow in this store holds (launch.rs).
  • main::start picks the slot, creates the worktree and the log, runs .flow/setup (often minutes: Docker), and only then appends the Workspace event that records the slot, so flow server opens the worker after setup. Between picking and recording, a second flow start can pick the same slot, even in one store.
  • Each project's tmux session sets FLOW_HOME, so its store, server, master and flows are its own; nothing connects the stores.

A. Slot claims: one file per taken slot in the shared folder recommended

flow start takes a slot by writing ~/.local/state/flow/slots/<n> naming its store and flow id, under a short lock (milliseconds, released before setup). A claim counts while its flow is unfinished in its store; a claim whose flow ended, was removed, or whose store is gone is free to take again. The log still records the slot in the Workspace event as today.

Gains
  • Race-free across projects and fixes the race inside one project: the claim exists before setup starts.
  • The lock is held for milliseconds; a slow setup blocks no one.
  • A claim cleans itself up: no flow, no claim; nothing to release by hand.
  • No new event kind; the log format stays as it is.
Costs
  • A second kind of state besides the logs (small files), though only ever trusted when its flow confirms it.
  • Checking a claim reads that flow's log in another store (one file per taken slot, at most 20).

B. Slots derived from every store's logs, under a lock held through setup

No claim files: flow start takes a global lock, folds every registered store's flows to find a free slot, and keeps the lock until its Workspace event is written, after setup.

Gains
  • The logs stay the only state; nothing extra can go stale.
Costs
  • Every flow start in every project waits while one project's setup runs (minutes with Docker).
  • Shortening the lock means recording the slot before setup: either a new event kind ("slot reserved"), a stored-data change, or the Workspace event early, so flow ui opens the worker before setup is done.
  • Folds every flow of every project on each start.

C. A fixed slot range per project

The registry gives each store its own band (project 1: 1-4, project 2: 5-8, ...), so slots never collide without any coordination at start time.

Gains
  • No locking or cross-store reads when starting a flow.
Costs
  • 20 slots split by project: a busy project runs out while others sit idle; a sixth project gets nothing.
  • Leaves the race inside one project as it is.
  • Bands have to be handed out and given back when a project goes away.

Shared by all three

  • Registry: any flow command registers its store once: a file ~/.local/state/flow/stores/<hash of the root> holding the store's path. A store whose folder is gone is skipped and dropped.
  • Overview: flow status --all lists every registered store's flows with a project column (TOON, and --json as a list of boards). In flow ui the board gets a key that switches to every project, grouped by project, read-only.

Recommendation: A

Only A is race-free without making one project wait for another's setup, and it fixes the race that already exists inside a project. Its extra state cannot lie: a claim only counts while the flow it names is unfinished, so a crash, a removed flow or a deleted store frees the slot by itself.
