Mismatched saaio binaries

0.2.0 · ROADMAP Planned soon · approaches · 2026-10-28

Reproduced

On a scratch store, with the real release binaries: cargo/saaio is 0.1.0 and comes first on PATH, local/saaio is 0.1.1 behind it.

  • Bare saaio runs 0.1.0 and starts a 0.1.0 server. The master pane gets SAAIO_MASTER=1 but no SAAIO_PROOF.
  • Run from the pane, 0.1.1's saaio send answers error: only the master sends. That is wrong: it is the master, but its server hands out no keys.
  • A 0.1.1 server is running and a 0.1.2 UI attaches: nothing is said. Both speak protocol 8.
  • Already covered: a 0.1.2 UI against a 0.1.0 server is refused (a saaio server of an earlier version still runs on /tmp/saaio-501/...; run `saaio --stop`). It names neither binary.

What exists today

  • proto::BUILD is 0.1.2 (45630ee). The client sends it in Hello as Peer { pid, cwd, build } (src/client.rs:52). The server only logs it.
  • ServerMsg::Welcome { version } (src/proto.rs:181) does not say which build the server is. So no client knows.
  • Another protocol: the server sends Refused (src/server/conn.rs:110) and the client appends "run `saaio --stop`" (src/client.rs:62).
  • Hooks run the server's own current_exe by absolute path (src/adapter.rs:99). An agent's saaio send runs whichever saaio its PATH finds first.
  • saaio update installs into the folder of current_exe (src/cli/commands/update.rs:44). Its help says in general terms that a running server keeps the old version.
  • Env does not read PATH (src/cli/env.rs).

All three approaches share the PATH check: the first executable saaio on PATH, compared with current_exe after both are canonicalised, and that binary's --version read with a 1 s deadline. They differ only in how a command finds out which build the running server is.

A. The server says who it is in the handshake recommended

Welcome carries the server's build and the executable it started from, recorded at startup. The protocol goes to 9. From 0.2.0 on, a server's Refused names its build and executable too. The UI compares builds when it attaches. saaio update connects as Control to each registered store's server and reads them. An old protocol-8 server refuses a 0.2.0 client: the client names the server's pid, and saaio --stop.

Builds on the handshake that already exists, where the request expects it. Nothing new is stored. The executable is the one the server started from, so it is still correct after an update replaced the file on disk.

The protocol bump means any 0.1.x server refuses a 0.2.0 UI until saaio --stop. A minor release would usually bring that anyway, and the refusal now explains it. A command without a UI has to connect to the server to learn its build.

B. The server writes server.json beside its socket

At start, the server writes its pid, build and executable into a private file next to the socket. Any command reads it without connecting and checks that the pid is still the one listening. No protocol change.

Works without a connection, so saaio send and status could name the server's build cheaply.

A second record of the same fact, which can go stale and needs a pid check. Every 0.1.x server lacks the file, so "no file but something listening" has to mean "an earlier saaio" anyway. It ignores the handshake that already carries the client's build.

C. Ask the OS which process listens

Take the peer pid of the socket (we already do this for --stop), get its executable path (ps -o comm= on macOS, /proc/<pid>/exe on Linux), and run <path> --version.

No server change. Works for every old server.

Wrong in exactly the case that matters. After saaio update renamed the new binary over the old path, --version on that path names the new build while the server still runs the old one. macOS gives no "(deleted)" marker. It also depends on parsing ps. Rejected.

Shared by all three

  • UI. On attach, if the server is another build or another saaio comes first on PATH, a dialog names both binaries and builds and saaio --stop. After it is dismissed, a short line stays in the title row, ahead of the update notice.
  • saaio update. After it installs, and also when the release is already the latest, it adds shadowed (the other saaio first on PATH, with its build) and servers[] (each running server whose build differs from this binary's), each with help naming saaio --stop.
  • saaio send. When the pane says master or flow but carries no SAAIO_PROOF, the refusal says the server hands out no keys, and names saaio --stop.

Recommendation

A. The handshake already carries the client's build, so making it carry the server's build is a small step. It is the only option that names the right build after an update replaced the file. Its one cost, a single saaio --stop when moving to 0.2.0, comes with a refusal that now says why.
