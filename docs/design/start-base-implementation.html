saaio 0.2.0 - design-code, step 2 of 2 - branch flow/start-base

Stacked flows: the implementation

1. Decision recap

Approach B: saaio start --base <branch> (and a base row in the new-flow dialog) creates the worktree from the base and records it on the Workspace event; the worker is told to target it. When the server learns that a flow's merge request merged, every unfinished flow standing on that flow's branch gets a base-merged event: its base moves to the branch the merge went into, and its worker hears it as news.

Decided: B over A (master only) and C (saaio rebases). The rebase stays with the worker.

5. Call chains

saaio start --base flow/shop-217 "SHOP-218 ..."

sequenceDiagram
  participant S as start::run
  participant G as git
  participant St as Store
  participant W as workspace
  S->>G: start_point(repo, base)
  G-->>S: Local / Remote
  G--xS: Err unknown base
  S->>St: create(Started)
  S->>W: create_worktree(repo, space, Some(from))
  W->>W: run(add_argv(.., from))
  S->>St: append(Workspace with base)
  1. start::run -> start::pick_base(&repo, args.base): Result<Option<StartPoint>, Failure>, right after pick_kind, before store.create.
  2. pick_base -> git::start_point(repo, base): Result<StartPoint>: check-ref-format --branch, then refs/heads/<base>, else for each remote (origin first) git fetch <remote> refs/heads/<base>:refs/remotes/<remote>/<base> under a deadline, the first that has it.
  3. start::run -> worktree::workspace_for(..), then Workspace { base: args.base, .. }.
  4. start::run -> workspace::create_worktree(&repo, &space, from.as_ref()): Result<()> -> process::run(&add_argv(repo, space, Some(&from.rev()))): git worktree add --no-track -b flow/shop-218 <path> flow/shop-217.
  5. Setup hook with SAAIO_BASE, then append_workspace (base recorded), then output::start::started with base.
  6. Server opens the pane: worker_spec -> Adapter::wiring(exe, trusted, space.base) -> worker_prompt(Some("flow/shop-217")); worker_env sets SAAIO_BASE.
Errors: an invalid name or a base no local branch or remote has fails in step 2 as Failure::error("no branch flow/x here or on origin", ["Run `git branch -a` to see the branches", "Push it first when it lives in another clone"]), exit 1, nothing created. A fetch past its deadline counts as "not on that remote". --base with --plain is a clap usage error, exit 2.

The base merges first

sequenceDiagram
  participant F as forge_watch
  participant K as stack
  participant St as Store
  participant D as deliver / wake
  participant Wk as worker B
  F->>F: forge::news(A) = Merged
  F->>St: append(A, Merged)
  F->>K: on_merge(board.flows, A, found.target)
  K-->>F: [(B, BaseMerged)]
  F->>St: append(B, BaseMerged)
  D->>St: undelivered(B)
  D-->>Wk: news from saaio: rebase onto main
  1. Server::forge_answer(Answer::Found { id: A, found }) folds A, forge::news(&flow, found) = Some(Merged), appends it (as today).
  2. When that kind is Merged: stack::on_merge(&self.board.flows, &flow, &found.target): Vec<(String, EventKind)>.
  3. Server::restack(events, now): store.append(id, &LogEvent::new(now, BaseMerged { base: "flow/shop-217", onto: "main" })) for each.
  4. The StoreWatch refolds B: workspace.base = "main", timeline "base flow/shop-217 merged, now on main". Status and --json show main.
  5. Claude Code worker: its saaio wait -> deliver::worker_news -> wake::undelivered: [Note::BaseMerged] -> wake::for_worker. Codex worker: server/news.rs::take_news, the same text typed once it is idle.
  6. The worker reads: "news from saaio: flow/shop-217, the branch this flow stands on, was merged into main. Rebase your own commits onto it (git fetch, git rebase --onto origin/main flow/shop-217, or origin/flow/shop-217 once that branch is gone), point your merge request at main and push with --force-with-lease." Later notes say the same for each later merge.
Errors: a failed append is logged to server.log (as forge news is), the other flows still get theirs. A flow already finished or merged gets nothing. B's own pane is never touched by the server's git.

New-flow dialog

  1. App opens the dialog: NewFlowForm::new(..) with bases = branches of the unfinished flows of that repo, Effect::LoadBranching(repo).
  2. ui.rs answers: app.on_branching(&repo, Branching::load(&repo), git::current_branch(&repo)) -> form.set_branching(branching, checked_out).
  3. Tab reaches Field::Base: typing edits form.base; up and down cycle form.bases; empty shows main (checked out) faint.
  4. Enter: Job::Start(form).args() adds --base <base>; a refused base comes back as the form's error under the request, like any failed start.

6. Conventions followed

  • Refuse before anything is created, with help lines: pick_agent, pick_kind (src/cli/commands/start.rs:142, :162).
  • Optional event field with serde(default, skip_serializing_if): Started.phases (src/event.rs:39).
  • Pure decision module beside a server reaction: forge::news + forge_watch::forge_answer (src/forge.rs:293, src/server/forge_watch.rs:161); stack.rs mirrors pause.rs, reconcile.rs.
  • git argv built in launch/worktree.rs and asserted as strings in its tests (src/launch/worktree.rs:112).
  • gh/glab always run in the main checkout, never the worktree (src/forge.rs:21); git fetch for the base runs there too.
  • New --json key without a version bump (docs/json.md, Versions).
  • master.md changes keep the old default as master-v12.md (src/server/master-v11.md).
  • Deviation: wake::undelivered counts two kinds. Kept in one count so "delivered" stays one number per flow in waits/.

8. Assumptions

  1. A local base wins over the remote's and is used as it is, not fetched or updated.
  2. The new branch never tracks the base (--no-track), so git pull and git push in the worktree do not touch the base.
  3. The new base after a merge is the branch the merge request actually went into (gh/glab), not a guess at the default branch.
  4. Only bases that are flows of the same store and repository are followed; a base nobody runs as a flow stays as typed.
  5. saaio remove of the base flow does not refuse because a flow stands on it; the stacked worktree keeps its commits.
  6. The master learns of a base merge from status and the worker's next stop; master.md gets two lines: start stacks with --base <the previous flow's branch>, and saaio tells stacked workers when a base merges.
  7. The board's sidebar and the status list stay unchanged; base shows in detail views only.
  8. --base takes a branch name only, not a flow name.

9. Decided in review

  1. Remote-only base: fetched from the remotes (origin first) under a deadline.
  2. Dialog base field: a text row, main (checked out) faint when empty, up and down fill in this repo's unfinished flows' branches.
  3. --base takes a branch name only.
  4. saaio remove of a base flow does not refuse for it, but names the flows standing on it: stacked[n] in its output and refusal, with a help line. stack::standing_on(flows, base) is shared with on_merge.
