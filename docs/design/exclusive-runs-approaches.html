saaio - design-code, phase 2 - 2026-11-04

One heavy run per project

When a worker's tool call runs a command listed in the repo's [exclusive] commands while another worker of the same project runs one, saaio holds the call until the first run ends. Three ways to build it; pick one.

What exists today

  • The hook already holds tool calls. saaio hook on PreToolUse sleeps in wait_for_services while a flow's services pause or resume, polling the flow's log every 200 ms (src/cli/commands/hook.rs:121, :158). Its PreToolUse timeout is 150 s for both harnesses (src/adapter/claude_code.rs:28, src/adapter/codex.rs:73).
  • Hooks talk to the store, not the server. The hook proves its session (SAAIO_PROOF), appends events to flows/<id>.jsonl and never prints to stdout. It works without a running server.
  • Both harnesses give the shell line. Claude Code and Codex send tool_input.command for Bash (src/adapter/codex.rs:176).
  • Repo config .saaio/config.toml is read only by Branching::load for [branch] (src/branching.rs:33); RepoConfig is private there.
  • The pane's agent leads its own session (portable-pty calls setsid, src/server/host.rs:379), so getsid(0) in the hook is the agent's pid. rustix with process is a dependency; nothing uses flock or reads the process table yet.
  • The sidebar shows a working flow's phase name (src/ui/sidebar/labels.rs:68); the board card already adds paused from FlowView.services (src/ui/board/cards.rs:292).
  • Store = project. A repository's flows share one store (projects/<name>); the shared folder spans the machine, which is where a machine-wide limit would live.

A. Hook gate, the turn kept by a watcher Recommended

The turn is a flock on a file in the store. The hook takes it (waiting and reporting "waits its turn" meanwhile), then hands the locked file to a small detached saaio process that watches the agent's process tree and lets go once no process under the agent runs a listed command. The kernel drops a flock when its holder dies, so no lock is ever stale.

New: lock file, watcher, Exclusive. Modified: hook, fold, view, sidebar.

Touches: cli/commands/hook.rs, a new exclusive.rs (config, matching, pure), turns.rs (the lock files, beside store.rs/private.rs which own file creation), a process-tree reader, event.rs, fold.rs, view.rs, sidebar and board labels, both adapters' PreToolUse timeout, docs.

Fit: extends the existing hold in the hook instead of a new mechanism; state reaches the UI through events like everything else; works without a server like the services hold does.

Gains

  • Same code for Claude Code and Codex; no change to the command the agent or the permission rules see.
  • Background runs, docker compose exec and Sail are covered: the watcher sees the processes, not the tool call.
  • Crash safe by the kernel: watcher killed, agent gone, process killed - all release.
  • Machine-wide later = lock folder in the shared folder, limit N = N lock files.

Costs

  • Reads the process table (ps) twice a second while a turn is held.
  • A grace window: if no listed process shows up within ~10 s (tool denied or failed to start), the turn is let go; a permission prompt extends it.
  • Waiter order is not strictly first-come.
  • PreToolUse timeout must rise to ~30 min, the longest a call can wait.

B. Rewrite the command to run under a lock

The hook answers PreToolUse with an updatedInput that wraps the line: saaio exclusive -- sh -c '<line>'. The wrapper takes the flock, runs the line and exits when it ends, so the turn is exactly the run's lifetime.

flowchart LR
  H["saaio hook (modified)
prints updatedInput"] --> T["harness runs
saaio exclusive -- sh -c line (new)"]
  T -->|"flock for its lifetime"| L[("store/turns/0.lock (new)")]
  T --> R["the heavy run"]

Gains

  • The turn ends exactly when the wrapped line ends; no process-table polling, no grace window.

Costs

  • Codex's PreToolUse has no verified way to rewrite input; Claude Code only.
  • Permission allowlists (Bash(php artisan test:*)) match the rewritten line, so allowed commands start asking.
  • The wait happens inside the tool: the worker shows working, not waiting its turn, unless the hook also waits.
  • Wrapping in sh -c changes quoting and loses a cd the agent relied on; the hook would print to stdout, which it never does today.

C. The server hands out turns

saaio server owns the turns: the hook asks over the socket, the server already knows every pane's pid, watches the trees and answers when it is the caller's turn. The UI state comes straight from the server.

flowchart LR
  H["saaio hook (modified)"] -->|"ask turn (new message)"| S["saaio server
turns.rs (new)"]
  S --> P["pane process trees"]
  S --> U["UI board"]

Gains

  • One owner of the state; fair first-come order; no extra process per turn.

Costs

  • Hooks gain a socket dependency and a new role in proto::allowed; without a server, calls run unheld.
  • One server per store: a machine-wide limit needs servers to coordinate, the growth path the request names.
  • A server restart loses every turn in flight.

Recommendation

A. It is the only one that meets every requirement on both harnesses: it holds before the call so the sidebar can say "waits its turn", the kernel makes stale locks impossible, the watcher keeps background runs' turns until their processes end, and moving the lock folder from the store to the shared folder is the whole machine-wide step. Its cost is a ps poll while a turn is held and a short grace window, both small next to a test suite.

Reply with A, B, C or a mix. Questions about matching, timeouts and the sidebar look come on the implementation page.
