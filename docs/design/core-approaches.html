design-code / phase 2 - piece 1+2 of 6: event format + flow CLI core

Who turns the event log into state and progress?

Every flow is an append-only event log the flow CLI writes. Somebody has to fold those events into what the board shows: current state, phase durations, task counts, blockers, timeline. Where that fold lives decides what the contract between the CLI and its readers (the Claude Code mod, flow status, other harnesses) is. Scope of this piece: flow report, flow status, flow list; flow start and the mod come later.

new duplicated logic existing / later piece

What exists today

  • Nothing yet at ~/projects/flow. Decided: new repo, Rust, append-only JSONL per flow, the CLI is the only writer (round 2, approach A).
  • Your most recent Rust CLI, wordstamp, sets the conventions: flat src/ modules per concern, clap derive (wordstamp/src/main.rs:19), anyhow at the edges, serde_json, dirs, inline #[cfg(test)] modules (src/align.rs:177).
  • The reader on the Claude Code side is a mod: it can read files ($.fs) and run processes ($.process.run), and plan-progress already polls every 2 s (plan-progress/hooks/register.tsx:24).

A. The CLI folds; readers ask flow status --json

recommended

The fold lives once, in Rust. flow status --json prints every flow already derived (state, phase steps with durations, tasks, blocker, timeline, decisions); flow status prints the same as a plain board. The event log becomes a private detail of the CLI. The contract is two command lines: flow report ... to write, flow status --json to read, with a version field in the JSON.

Touches

New: CLI modules for events, store, fold, report, status. Later the mod runs flow status --json every 2 s instead of parsing files.

Gains

  • One implementation of "what does this flow look like" - every reader shows the same thing.
  • The log format can change freely; only the status JSON is a contract.
  • The mod gets thin: run, parse, draw. Fold is unit-tested in Rust.

Costs

  • One process start every 2 s while the board is open (a Rust binary starts in a few ms).
  • The board shows nothing without the binary - it needs a clear "install flow" message.

B. Readers fold the raw logs themselves

The JSONL event format is the contract. The CLI folds for flow status; the mod reads the files with $.fs and folds them again in TypeScript.

Touches

Same CLI modules; plus a TypeScript fold in the mod, kept equal to the Rust one.

Gains

  • No process per refresh; the board reads files like plan-progress reads its plan.
  • The board works from the files alone.

Costs

  • Two folds that must agree on every rule (blocked survives a turn end, durations, not responding) - they will drift.
  • The raw format is frozen for every reader; every change is a migration in two languages.

C. The CLI writes a derived snapshot next to each log considered

Each flow report appends the event and rewrites <id>.view.json (atomically, via rename); readers read snapshots, no process needed. One fold, no process per refresh - but time-dependent fields ("4m ago", "not responding") still have to be computed by every reader, the snapshot is a second contract next to flow status --json, and a crash between append and rename leaves them out of step. A good later optimisation if process starts ever show up; not worth the second contract now.

Recommendation: A

The derived view is where the real rules live, so it should exist once and be tested once. A few milliseconds of process start every 2 s is cheap against two folds drifting apart, and keeping the log private means the format can grow (decisions, review items, auto mode) without touching any reader.
