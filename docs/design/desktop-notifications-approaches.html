Desktop notifications: approaches

When a flow starts waiting or is blocked, the UI makes the terminal raise a desktop notification. One decision here: whether the UI also tracks if the terminal itself has focus.

What exists today

  • App::on_server(ServerMsg::Board) already diffs the new board against the last one, flow by flow, to light a row that changed state (src/ui/app/messages.rs:31). The first board after start has nothing to diff against, so it lights nothing. That is the natural place for "one per transition, none on startup".
  • App is pure: it returns Effects, and ui::run does the I/O (src/ui.rs:233). Copying is the sibling: Effect::Copy -> Clipboard::copy writes OSC 52 to stdout, its choice of command made once from the environment in Clipboard::new(ssh, wayland, x11) (src/ui/clipboard.rs:19).
  • The master already has an "unseen" idea: it came to rest while not focused (messages.rs:157).
  • Focus reporting (mode 1004) is only mirrored from the focused pane (src/ui/outer.rs:104); Router passes ESC [ I / ESC [ O through as plain bytes. So today saaio does not know whether the terminal has focus.
  • [ui] holds prefix and update_check (src/config.rs:102); the new switch goes beside them.

Sending several at once doubles the notification in Ghostty and WezTerm, so saaio sends exactly one: OSC 9 by default, OSC 777 when TERM is foot or rxvt or VTE_VERSION is set. The text starts with "saaio:" so ConEmu and Windows Terminal never read it as their numbered 9;n commands. Inside tmux ($TMUX) the sequence is wrapped in tmux's DCS passthrough, which needs set -g allow-passthrough on (documented, like set-clipboard for OSC 52). No daemon, no new crate.

Sources: kitty docs, Ghostty OSC 9/777 commit, Ghostty OSC 99 discussion, tmux passthrough write-up.

A. Focus-aware Recommended

The App detects the transition in the board diff and returns Effect::Notify; a new ui/notify.rs (Notifier, built from the environment like Clipboard) writes the one sequence. Outer keeps focus reporting on always, the way it keeps the mouse on, and Router turns ESC [ I / ESC [ O into Routed::Focus(bool), still passing them to a pane that asked for them. A flow notifies when it is not in view, or when the terminal has lost focus, even the flow in view.

Catches the case that matters most: you are in the browser and the worker you were watching asks a question. Fits the Elm core and the Clipboard sibling exactly.

Focus events now always arrive, so the Router must swallow them for panes that did not ask, in pane and modal views alike; a bug there types [I into a session. A terminal without 1004 never says "unfocused", so saaio assumes focused and falls back to B's behaviour.

B. Out of view only

Same Notifier and Effect::Notify, no focus tracking: a flow notifies only when its pane is not the one in view.

  S[server Board] --> A[App]
  A -- "Effect::Notify" --> L[ui::run loop]
  L --> N[Notifier]
  N -- "OSC 9 / 777" --> T[real terminal]
  classDef new fill:#a3be8c,stroke:#2e3440,color:#2e3440
  classDef mod fill:#ebcb8b,stroke:#2e3440,color:#2e3440
  class N new
  class A,L mod

Touches: the same minus input.rs and outer.rs.

Smaller; input handling stays exactly as it is.

Misses the flow in view while you work in another window, and notifies about flows out of view while you look straight at the sidebar. Adding focus later means this same change to the Router anyway.

Rejected

  • Notify from saaio server. The server owns the sessions but not the terminal: only the attached UI knows what is in view and where its stdout goes. It would need a new proto message for no gain, since a detached server has no terminal to notify through.
  • Send OSC 9, 777 and 99 together. Two notifications per transition in Ghostty and WezTerm.
  • A notifier command (osascript, notify-send). Breaks over SSH and in tmux on a remote box, and is the "extra daemon" the request rules out.

Recommendation

A. The point of a desktop notification is reaching you when you are not looking at saaio, and only focus tells that. The extra Router work is small and testable as pure byte routing.
