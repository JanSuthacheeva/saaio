Configurable workflow

1. Decision recap

Approach A: each flow records its phase names in its started event when it starts, and fold builds the steps from the log, never from config. The workflow (1 to 4 phases, each with a name and the skills that start it) and the worker's first prompt move into config.toml.

  • At most 4 phases. This keeps the steps row as wide as today and gives every position a built-in color.
  • Defaults: plan, implement, review, merge-request, with today's four skills. Logs without a recorded list read design as plan.
  • The first prompt: an agent's own prompt wins; else [worker] prompt, when set, exactly as written; else the built-in default (claude /ship-feature {request}, codex $ship-feature {request}). No rewriting between harnesses.
  • JSON VIEW_VERSION 3. theme.toml [phase] colors any phase by name.

3. Units

src/workflow.rs new

The phases a flow walks through and the skills that start each; replaces config::PhaseMap and config::builtin_phases.

pub const MAX_PHASES: usize = 4;

/// One [[phases]] entry: its name and the skills that start it.
#[derive(Debug, Clone, PartialEq, Eq, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct PhaseSpec {
    pub name: Phase,
    #[serde(default)]
    pub skills: Vec<String>,
}

/// 1 to MAX_PHASES phases with distinct names, no skill in two.
#[derive(Debug, Clone, PartialEq, Eq, Deserialize)]
#[serde(try_from = "Vec<PhaseSpec>")]
pub struct Workflow { phases: Vec<PhaseSpec> }

impl Default for Workflow { fn default() -> Workflow; }          // builtin()
impl TryFrom<Vec<PhaseSpec>> for Workflow { type Error = String; ... }

impl Workflow {
    /// plan design-code, implement implement-plan, review review-changes,
    /// merge-request write-merge-request.
    pub fn builtin() -> Workflow;
    /// The names in order: what flow start records.
    pub fn phases(&self) -> Vec<Phase>;
    /// "/design-code" and "plugin:design-code" both find design-code's phase.
    pub fn phase_of(&self, skill: &str) -> Option<Phase>;
}

try_from errors: "a workflow has 1 to 4 phases", "two phases are named review", "design-code starts two phases", "Phase is lowercase letters, digits and -". serde puts them on the toml line.

6. Conventions followed

  • A refused old config key names the new one, as the top-level agent key does (config.rs:113).
  • Built-ins under the file's values, as add_builtins does (config.rs:127); except that the workflow is replaced whole, since merging two ordered lists has no clear meaning.
  • An optional field on an existing event, as Workspace.branch/slot grew for plain sessions (event.rs:337 test).
  • Validation through serde try_from, so the error carries the line, as Prefix does for [ui] prefix (config.rs:518 test).
  • One module per noun: workflow.rs, a top-level private module in lib.rs, as branching.rs.
  • Deviation: Phase loses Copy and the theme's Palette loses Copy; both now hold strings.

7. Test seams

  • workflow.rs: unit tests for builtin, phases, phase_of (slash and plugin prefix), each try_from error.
  • event.rs: Phase name rules; Started round-trips with and without phases; an old started line parses.
  • fold/tests.rs: custom 3-phase steps; design-to-plan only without a list; unknown phase ignored; MR enters the last phase.
  • config.rs: [[phases]] read, limits, old [phases] refused; the prompt order (own, [worker], built-in default, none).
  • adapter: translate fixtures with a Workflow.
  • theme.rs, theme_file.rs: color by name, by position, "design" alias, bad name error.
  • tests/cli.rs: start/new record phases; report refuses an unknown phase; status --json version 3. Goldens rewritten where "designing" or "design" showed.

8. Assumptions

  1. A [[phases]] list replaces the built-in workflow whole; it is not merged with it.
  2. A phase event a flow has no phase for is ignored by fold, so the hook appends nothing for it.
  3. A merge-request event enters the flow's last phase, whatever it is called.
  4. A phase without a color in the theme takes the built-in color of its position (1st to 4th).
  5. A [phase] color can name a [ui] or [state] key; nothing can name a phase's color.
  6. A delegated card says "review · agent", not "reviewing · agent": no gerunds for names flow does not know.
  7. An [agents.claude] in the file without a prompt, and no [worker] prompt, keeps the built-in claude prompt.
  8. flow new records the configured workflow too, so it now reads config.toml (and fails on a broken one).

9. Decided in review

  1. The old [phases] skill table is refused, with an error naming the [[phases]] shape.
  2. Phase names are lowercase letters, digits and -.
  3. A workflow has 1 to 4 phases.
  4. No / to $ rewrite for Codex: [worker] prompt, when set, overrides both built-in prompts exactly as written; an agent's own prompt still wins.
