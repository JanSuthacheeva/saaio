Configurable workflow

Users should not be tied to your four skills. The phases a flow walks through (names, order, the skills that start each) and the worker's first prompt move into config.toml. The defaults stay what they are today, with design renamed to plan.

What exists today

  • Phase is a closed enum of four: Design, Implement, Review, MergeRequest with ALL, index and name (src/event.rs:87). clap parses it for flow report phase (cli/commands/report.rs:21).
  • The skill map is already configurable: [phases] maps a skill name to one of the four (config.rs:14, builtin_phases at config.rs:182). The adapters look a skill up with adapter::phase_of (adapter.rs:162). So users can point their own skills at the four phases, but cannot name, add, drop or reorder phases.
  • fold builds steps from Phase::ALL with fixed-size arrays (fold.rs:124, fold.rs:326). A merge-request event forces the phase to MergeRequest (fold.rs:240). fold has about 15 callers (status, report, hook, start, new, send, remove, deliver, server panes) and none of them pass config.
  • The theme has four fixed phase keys (PaletteKey::Design..MergeRequest, ui/theme.rs:168) under [phase] in theme.toml. Cards use gerunds per phase, "designing", "implementing" (ui/board/cards.rs:375).
  • The first prompt is per agent: [agents.claude] prompt = "/ship-feature {request}", [agents.codex] prompt = "$ship-feature {request}" (config.rs:206, config.rs:212). Changing the workflow skill means overriding every agent.
  • JSON is VIEW_VERSION = 2 (view.rs:7); phase and steps[].phase are already strings on the wire.

The same in every approach

  • Phase becomes a name, Phase(String), serialised as the same string. The event log format does not change for phase events.
  • The config gets an ordered list, which replaces the [phases] skill map: 
    [[phases]]
name = "plan"
skills = ["design-code"]

[[phases]]
name = "implement"
skills = ["implement-plan"]
...
    Without the list, the built-in four. A file with the old [phases] table is refused with a message that names the new shape, as the old top-level agent key is (config.rs:113).
  • flow report phase <name> takes any name and refuses one the flow does not have, listing the ones it has.
  • Theme: [phase] in theme.toml takes any phase name. A phase without a color takes the built-in phase color at its position (1st, 2nd, ...), so a custom workflow is colored without a theme file. design in an old theme file reads as plan.
  • VIEW_VERSION 3: phase is any configured name, never design.

The approaches differ in one place: where a flow's list of phases comes from when its log is folded.

newmodifiedexisting

A. Each flow records its phases when it starts recommended

flow start and flow new write the configured phase names into the flow's started event. fold reads the steps from the log, so it stays pure and none of its 15 callers change. A log without the list was written before this change: it folds with the built-in four, and its design events read as plan.

Config.phases (list)->flow start / new->Started { ..., phases }->log
log->fold (steps from Started)->FlowView.steps->ui, status, --json
Config.phases->Workflow::phase_of(skill)->flow hook

Gains

  • A running flow keeps the workflow it started with; editing config.toml never relabels it.
  • fold stays a pure function of the log, the rule the crate already follows (CLAUDE.md: readers depend on the log, not the config).
  • The design alias has a precise boundary: only logs without a recorded list.
  • The server, status and the master all see the same steps.

Costs

  • One optional field on started; an older flow binary ignores it (serde skips unknown fields).
  • A config change reaches only new flows. To change a running flow's phases you start it again.

B. Fold reads the phases from config

fold::fold, views and board take a &Workflow. Every caller loads the config and passes it. The log keeps only phase names.

Config.phases->15 fold callers->fold(&workflow, ...)->FlowView.steps

Gains

  • No change to any event.
  • A config edit shows on every flow at once.

Costs

  • Fold depends on config: the server, deliver, every command and their tests thread a workflow through.
  • A running flow is relabelled when config changes; a phase it reported that is no longer listed has no step to show.
  • flow status --all folds other projects' logs with this user's config, fine today but wrong once config is per project.
  • The design alias must apply to every log, so a user cannot name a phase design.

Rejected: phases per repository

Putting the list in the repo's .flow/config.toml, next to [branch] (branching.rs), would let a team share one workflow. The skills are the user's, not the repo's, so the request's config.toml fits better. Approach A leaves the door open: a later repo setting only changes what flow start records.

The worker's first prompt

[worker] prompt = "/ship-feature {request}" becomes the one place to set it. An agent's own prompt becomes optional and still wins when set (aider keeps "{request}"). The built-in claude and codex agents lose theirs, so both follow [worker] prompt.

Codex calls a skill $name, not /name. So the Codex adapter turns a leading /skill of the prompt into $skill, and one [worker] prompt works for both harnesses. The alternative is to keep per-agent prompts as they are and have [worker] prompt only fill agents that set none; then a user who changes it must also override [agents.codex] prompt.

Recommendation

A, with the Codex rewrite for the prompt. It keeps fold pure, gives running flows a stable workflow, and makes the design alias exact. The price is one optional field on the started event.

Please choose A or B (or a mix), and say whether the Codex / to $ rewrite is right.
