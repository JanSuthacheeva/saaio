Codex as a worker harness

OpenAI Codex CLI as a second harness next to Claude Code, for workers and for the master: flow starts it, follows it through its own hooks, resumes it, and passes it the master's messages. The facts below come from the Codex source (openai/codex@6b99197, 0.163.0) and a live probe of the installed 0.144.1.

What exists today

  • Adapter is an enum with one variant, ClaudeCode (src/adapter/mod.rs:14). Its wiring puts --settings <hooks json> and the worker prompt right after the program (launch.rs worker_spec, line 138). translate turns one hook payload into EventKinds.
  • flow hook claude-code (main.rs:429) reads stdin, translates, and appends only what changes the flow. It always exits 0 and prints nothing.
  • A worker's Claude session id is the flow id: --session-id {id} on start, --resume {id} later (config.rs builtin_agents). Peek finds ~/.claude/projects/*/<id>.jsonl the same way (ui/peek.rs:39).
  • The master's messages reach a worker through an asyncRewake hook that runs flow wait. Exit 2 wakes an idle session (claude_code.rs:84, main.rs:374).
  • config.rs already accepts a user-defined [agents.codex], with {id}, {name}, {prompt} and {request} filled in.

The same in every approach

  • Adapter::Codex and adapter/codex.rs, with the same shape as claude_code.rs. Its translation tests run against payloads recorded from a real Codex.
  • flow learns the Codex session id from the first hook and stores it in the flow's log. Resume then fills a new {session} placeholder: codex resume {session}.
  • The worker prompt goes in through -c developer_instructions=.... The master's messages go out through the worker's synchronous Stop hook, since Codex has no flow wait.
  • A built-in codex agent, so flow start --agent codex works without a config file.
  • Codex can be the master too. Its instructions come from -c model_instructions_file or developer_instructions, read from master.md. Its session id is learned from its first hook into master.json, since flow cannot choose it. It resumes with codex resume {session}.
  • The skills stay agent-agnostic. A Codex session shows its review pages with lavish, styled from dotfiles-v2/agents/design-system.

Waking a session that cannot wake itself

A Claude session wakes itself through flow wait and asyncRewake. A Codex session cannot, so Adapter gets a capability that says which kind it is. For a Codex session, news is delivered in two places:

  • Busy: its synchronous Stop hook (flow hook codex) finds the news and exits 2, and Codex goes on with it. This covers messages for a worker and stopped flows for the master.
  • Idle: flow server already folds every log, so it sees the news itself and types it into the pane, followed by Enter.

Both places mark the news as delivered or seen in the same waits/ files flow wait uses, so nothing is delivered twice.

The approaches differ in one place only: how flow gets its hooks into Codex and past Codex's trust review.

newmodifiedexisting

A. Hooks per launch, reviewed once in Codex recommended

This works like the Claude adapter today. Adapter::Codex::wiring passes the hooks as -c hooks.<Event>=[...] arguments on every start and resume. The first Codex worker shows Codex's own hooks review in its pane. You press t once, and Codex remembers that trust until flow's hook definition changes (a new flow binary path, or a new event).

launch::worker_spec->Adapter::Codex.wiring->codex -c hooks.* -c developer_instructions ...
codex hook (stdin JSON)->flow hook codex->codex::translate->store.append

Gains

  • Mirrors claude_code::settings and worker_spec's splice exactly.
  • Touches none of your files. Codex itself records the trust.
  • Your own unreviewed hooks stay off.

Costs

  • One modal on the first Codex worker, and again after a flow update that changes the hooks.
  • Trust is keyed by position (stop:0:0), so another tool's session-flag hooks would collide. This is unlikely.

B. Hooks per launch, trust bypassed

This is approach A plus --dangerously-bypass-hook-trust on every launch. There is never a modal.

Adapter::Codex.wiring->codex --dangerously-bypass-hook-trust -c hooks.* ...

Gains

  • No first-run step at all.

Costs

  • Every untrusted hook runs, including project .codex/ hooks from a cloned repo. That defeats Codex's guard against prompt injection.
  • Codex prints a warning banner in every worker.

C. Hooks installed once into ~/.codex

A new flow setup codex writes flow's hooks into ~/.codex/hooks.json once. Every Codex session then runs flow hook codex, which does nothing without FLOW_ID. The launch passes only the worker prompt.

flow setup codex->~/.codex/hooks.json
any codex session->flow hook codex->nothing without FLOW_ID

Gains

  • One review, and it survives flow updates if the path stays the same.
  • A codex started by hand in a worktree still reports.

Costs

  • Writes into a dotfile you manage (dotfiles-v2) and needs a new command plus an uninstall.
  • Every Codex session on the machine spawns flow on every tool call.
  • Breaks the pattern the Claude adapter set (wiring per launch, nothing installed).

Rejected

  • notify only. It fires only at turn end, so there are no tools, permissions or skills. The source marks it legacy ("TODO: Remove").
  • Pre-seeding trust hashes through -c hooks.state. It works in theory, but flow would have to copy Codex's internal hash of the normalised hook. That breaks silently whenever Codex changes the hash.
  • A private CODEX_HOME per worker. It loses your login, sessions and config.

Decisions for you

1. Approach

A, B or C. I recommend A.

2. News for an idle Codex session

No hook can wake an idle Codex session. That is exactly when it matters: a worker waits for the master's answer, and the master waits for workers to stop. Options:

  • (a) Hold the news until the session's next Stop. In practice it waits until you type something in that pane, which makes a Codex master blind.
  • (b) Recommended: flow server types it into the pane, with a guard. It types only when the session is idle (its last hook was Stop) and no key has gone into that pane for 10 seconds. That guard matters most in the master pane, where you type most. Text you typed and left unsent stays in Codex's prompt, so typed news would be appended to it. The quiet period makes that rare, but not impossible.

2b. Choosing the master's harness

Today the master is the built-in master agent, which is Claude. Recommended: add [master] agent = "codex" in config.toml, with a built-in codex-master agent behind it. The default stays Claude.

3. A new event in the log

A session event that records the harness's own session id and transcript path. It is new stored data, and old flow binaries would ignore it. Recommended: yes. The alternative, searching ~/.codex/sessions by folder, guesses.

4. Scope

In this plan or later? (i) A peek for Codex workers, which reads the rollout JSONL. (ii) An agent row in the new-flow dialog, which today always uses the default agent. Recommended: both in. Without them a Codex worker is a second-class citizen in flow ui.

Outside this repo: the agent-skills (design-code, implement-plan, review-changes, write-merge-request, ship-feature) have to be linked into ~/.agents/skills for Codex to find them. Today only clickup-axi, commit, lavish and a few others are there.
