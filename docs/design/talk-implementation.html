design-code / phase 3 - review the implementation

The master and its workers talk to each other

new modified unchanged Claude Code

1. Decision recap

flow send <flow> "<text>" appends a Message event to the flow's log. Every Claude Code session flow starts, the master included, runs flow wait as an asyncRewake hook on SessionStart and Stop. The hook sleeps until there is news for its session, prints it and exits 2, and Claude Code then wakes the session with it.

Decided in phase 2: approach A, and the flow's mode decides who answers. The master answers an auto flow's questions when the code, the plan or your earlier decisions settle them. A guided flow's questions go to you, and the master relays your answer.

src/wake.rs new - pure

Decides what counts as news for a session. It has no I/O.

/// Each flow id -> the changed_at the master was last woken for.
pub type Seen = BTreeMap<String, u64>;

/// The master's messages in a flow's log after the first `delivered` of them.
pub fn undelivered(events: &[Event], delivered: usize) -> Vec<&str>;

/// Flows whose state needs the master (waiting, blocked, idle, done, not responding) and that
/// changed since it last saw them, oldest change first.
pub fn changed_flows<'a>(flows: &'a [FlowView], seen: &Seen) -> Vec<&'a FlowView>;

/// Seen after the master was told about `flows`.
pub fn mark_seen(seen: &mut Seen, flows: &[&FlowView]);

/// A first Seen, when none is stored yet: every finished flow, so only unfinished ones are news.
pub fn first_seen(flows: &[FlowView]) -> Seen;

/// Whose wait: the master's or a flow's worker's.
pub enum Waiter { Master, Flow(String) }

impl Store {
    /// Makes `pid` the session's one waiter (waits/<key>.pid); an older waiter sees it is replaced.
    pub fn claim_waiter(&self, waiter: &Waiter, pid: u32) -> Result<()>;
    /// The pid of the session's current waiter.
    pub fn waiter(&self, waiter: &Waiter) -> Option<u32>;
    /// How many master messages the flow's worker was given (waits/<id>.delivered), 0 without the file.
    pub fn delivered(&self, id: &str) -> usize;

    /// The master's Seen (waits/master.seen, JSON); None before the first wake.
    pub fn seen(&self) -> Option<Seen>;
    pub fn set_seen(&self, seen: &Seen) -> Result<()>;
}

The new rules in master.md:

  • flow wakes you with the flows that changed.
  • For an auto flow, answer what the code, the plan or the user's earlier decisions settle with flow send, then tell the user what you answered.
  • For a guided flow, tell the user, and send their answer when they give it.
  • Read a worker's whole answer with flow status <name> --full, and its code with git -C <worktree>.
  • Do not send a worker anything it did not ask for unless the user says so.

src/main.rs modified

enum Command {
    ..
    /// Tell a flow's worker something: an answer, an instruction, a correction
    Send { /// Flow name or id
           flow: String,
           /// What to tell it
           text: String },
    /// What a session's asyncRewake hook runs: sleeps until there is news for it, prints it, exits 2
    #[command(hide = true)]
    Wait { /// The master's news: flows that changed [default: $FLOW_ID's messages]
           #[arg(long)] master: bool },
}

/// Appends Message { text } to the flow; refused from a worker ($FLOW_ID set), for a finished
/// flow, one with no worker (no workspace), and an empty text or one over MESSAGE_LIMIT.
fn send(store: &Store, flow: &str, text: &str, now: u64) -> Result<Document, Failure>;

/// The news that ends the wait; None when the waiter was replaced, its flow is gone or its
/// session ended (parent pid changed).
fn wait(store: &Store, waiter: &Waiter, clock: fn() -> u64) -> Option<String>;
// main(): Command::Wait is handled before the store lookup's output, like Hook: Some(news) ->
// eprint!(news), exit 2; None -> exit 0. It never prints to stdout.

Constants: MESSAGE_LIMIT = 4000 chars; WAIT_EVERY = 500 ms, the same as the server's WATCH_EVERY; SETTLE = 2 s, how long the master's waiter keeps collecting after the first change so that several flows arrive as one wake.

5. Call chains

a. The master answers a worker

  1. master -> main::send(store, "shop-217", text, now): Document
  2. main::send -> views(store, now) -> fold::resolve(&flows, "shop-217"): Option<&FlowView>
  3. main::send -> Store::append(&id, &Event::new(now, Message { text })): Result<()>
  4. main::send -> output::sent(&flow): Document ("sent")
  5. worker's wait loop -> Store::events(&id) -> wake::undelivered(&events, Store::delivered(&id)): ["..."]
  6. wait -> Store::waiter(&Waiter::Flow(id)) == own pid -> Store::set_delivered(&id, n)
  7. wait -> output::news_for_worker(&messages): String -> main: eprint, exit 2 -> Claude Code wakes the worker
  8. worker works; its hooks append Working, then at Stop Answer and Idle/Waiting, which wakes the master again (chain b)

Errors:

  • Step 2 finds no flow: exit 1, no flow shop-217, help flow status.
  • The flow is done or ended: exit 1, shop-217 is finished.
  • The flow has no workspace: exit 1, shop-217 has no worker; it was not started with flow start.
  • $FLOW_ID is set: exit 1, only the master sends; end your turn with the question instead.
  • The text is empty or too long: exit 2 (usage).
  • The worker's session is not running, for example because flow ui is stopped: the message waits in the log, and the SessionStart waiter delivers it when the pane opens again.

b. A worker asks, and the master wakes

  1. worker Stop -> main::hook -> claude_code::translate: [Answer { text }, Waiting { question }] -> Store::append each
  2. master's wait loop -> views(store, now): Vec<FlowView> -> wake::changed_flows(&flows, &seen): [shop-217]
  3. wait -> sleep SETTLE -> views again -> wake::changed_flows: [shop-217, any others that changed meanwhile]
  4. wait -> Store::waiter(&Waiter::Master) == own pid -> wake::mark_seen(&mut seen, &changed) -> Store::set_seen(&seen)
  5. wait -> output::news_for_master(&changed): String -> main: eprint, exit 2 -> Claude Code wakes the master
  6. master (master.md): auto -> reads code, flow status shop-217 --full -> chain a; guided -> tells you which flow asks what

Errors and edges:

  • No master.seen yet: wake::first_seen marks finished flows as seen, so the first wake lists only unfinished flows that need the master.
  • A log does not parse: that flow is skipped, the same as in flow status.
  • A file write fails: the waiter prints nothing and exits 0. The next turn end arms a new waiter.

c. Arming, replacing and ending a waiter

  1. Claude Code SessionStart or Stop -> spawns flow wait [--master] in the background (asyncRewake), stdin = the hook payload, which is ignored
  2. main -> Waiter from --master or $FLOW_ID; neither -> exit 0
  3. main::wait -> Store::claim_waiter(&waiter, std::process::id())
  4. loop every WAIT_EVERY: Store::waiter(&waiter) != own pid -> None (replaced by the next turn end's waiter)
  5. loop: the parent pid changed (Claude Code exited) -> None; a worker's flow is removed or finished -> None
  6. loop: news -> Some(text) as in chains a and b

Mid-turn: a waiter armed at the last turn end is still running while its session works. When it fires, Claude Code hands its text to the running turn, so a correction reaches a busy worker without waiting for the turn to end. The implementation's end-to-end check verifies this.

6. Conventions followed

  • A command appends an event and the fold derives the rest (main.rs report, src/main.rs:625). flow send is a report the master makes about a flow.
  • Hidden plumbing commands, like Hook (src/main.rs:119), and exit-code handling before stdout output, like run_hook (src/main.rs:194).
  • File operations only in store.rs (CLAUDE.md "store.rs - every file operation"). The waiter files sit beside flows/, as .alive heartbeats do (src/store.rs:163).
  • Pure decisions in their own module, tested without I/O, like server/reconcile.rs and fold.rs.
  • The adapter owns the harness specifics: Adapter::wiring (src/adapter/mod.rs:36), now joined by master_wiring. Wiring is inserted after the program, fresh and resumed, as worker_spec does (src/launch.rs:143).
  • Earlier defaults of master.md are replaced only when unedited (PREVIOUS_DEFAULTS, src/server/master.rs:18).
  • Deviation: flow wait writes to stderr and exits 2 on success. That is Claude Code's asyncRewake contract, and the reason it is handled before the normal stdout path.

7. Test seams

  • wake.rs: unit tests over hand-built events and views: undelivered counts, which states and changes count, first_seen.
  • store.rs: claim, replace and read a waiter; delivered and seen round trips; remove cleans waits/.
  • fold.rs: Message adds a timeline entry and leaves the state; Answer sets answer; changes for both.
  • claude_code.rs: settings carry the asyncRewake waiter on SessionStart and Stop; master_settings only that; Stop yields Answer then Waiting/Idle (fixture stop_waiting.json).
  • master.rs: spec wires wait --master fresh and resumed; v2 default is replaced.
  • tests/cli.rs: flow send's refusals and its event; flow wait as a process: exits 2 with the message once one is appended, 0 when a second waiter replaces it, the master's sees a waiting flow.
  • End-to-end: flow ui with a real auto and guided worker; the master is woken by each and answers or relays.

8. Assumptions

  1. Only the master sends. A worker asks by ending its turn with the question, as today, and there is no worker-to-master or worker-to-worker message.
  2. The master is woken for waiting, blocked, idle, done and not responding. In a guided flow that includes every phase stop, which is what tells you a design is ready to review.
  3. Several changes within 2 seconds arrive as one wake.
  4. A message does not change the flow's state. The state changes once the worker acts on it.
  5. The worker sees "message from the flow master:" as a hook message, not as your words.
  6. The diff stays git's job: the master runs git -C <worktree>, and flow does not add commits or files to flow status.
  7. The master's waiter watches its own project's store only, not --all.
  8. Agents without a Claude Code adapter get no waiter. flow send still records the message for when their adapter can deliver it.

9. Decided in review

  • Every idle turn end wakes the master, in guided and auto flows.
  • The wake-ups can be switched off: [master] wake = false in ~/.config/flow/config.toml (default true). Config gains master: MasterConfig { wake: bool }; MasterRecord::spec takes wake: bool and leaves the master's waiter out when it is false. Workers keep theirs, so flow send still works.
