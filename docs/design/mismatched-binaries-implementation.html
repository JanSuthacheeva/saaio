Mismatched saaio binaries

0.2.0 · implementation design · approach A, the handshake · 2026-10-28

Decision recap

The server's Welcome says which build it is and which binary it started from (protocol 9, the bump in its own commit). The UI and saaio update compare that build with their own, and with the first saaio on PATH, and name both binaries and saaio --stop when they differ.

Decided in phase 2: shared parts as proposed (the UI dialog plus a title-row line, shadowed and servers[] in saaio update, the clearer saaio send refusal). The refusal from a 0.1.x server tells the user exactly to run saaio --stop. The kinds-of-flows flow may bump the protocol too: whichever merges second takes the next number.

src/binaries.rs new

The saaio binaries that can disagree (this one, the first on PATH, a server's) and how they differ.

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct Binary {
    pub exe: PathBuf,
    /// proto::BUILD's form: `0.1.2 (45630ee)`; `unknown` when --version said nothing usable.
    pub build: String,
}

impl Binary {
    /// This process: current_exe and BUILD.
    pub fn this() -> io::Result<Binary>;
    /// The version part of the build: `0.1.2`.
    pub fn version(&self) -> &str;
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum Mismatch {
    /// Another saaio of another build comes first on PATH.
    Shadowed(Binary),
    /// The running server is another build.
    Server(Binary),
}

/// The first executable file named saaio in `path`'s folders; empty and relative entries skipped.
pub fn first_on_path(path: &OsStr) -> Option<PathBuf>;

/// The first saaio on PATH when it is another file than `this` (canonicalised) and its
/// `--version` (1 s) names another build or none.
pub fn shadowing(this: &Binary, path: &OsStr) -> Option<Binary>;

/// Shadowed first, then Server when `server`'s build is not `this`'s.
pub fn mismatches(this: &Binary, server: Option<&Binary>, path: Option<&OsStr>) -> Vec<Mismatch>;

  1. commands::ui::attach -> ui::run(socket, UiEnv { path, .. }, clock)
  2. ui::run -> Client::connect(socket, Role::Attach{..}): Result<Option<Client>>
  3. Conn::hello -> ServerMsg::Welcome { version: 9, server: Binary { exe: flow_exe, build: BUILD } }

Errors. Another protocol: Conn::hello sends Refused. Client::connect adds the server's pid (peer_pid) and this binary, ending in "run `saaio --stop`, then start saaio again; unfinished flows resume". ui fails and the person reads that line. If Binary::this fails (current_exe unreadable), there are no warnings and the UI runs. A --version that fails or times out counts as build unknown, which is shadowed.

Conventions followed

  • A wire change goes with a protocol bump, and the server reports the reason in Refused (src/server/conn.rs:110-124).
  • Probing --version with a deadline reuses system::version (src/system.rs:87), as bug-report does.
  • Environment variables are read only in main.rs, into Env (clippy.toml disallowed-methods). current_exe is read by the code that needs it (CLAUDE.md, cli).
  • Over-session boxes use Dialog, as dialog::help does (src/ui/dialog.rs). The title row's right side has the priority order notice, then update (src/ui/app/chrome.rs:24).
  • TOON documents carry help[] next steps (src/cli/output/update.rs:10).
  • Paths shown with ~ (Env::bin_path src/cli/env.rs:189, App::tilde).
  • Deviation: proto imports binaries for a wire type. proto already imports view for Board, and the layering test keeps this free of cycles.

Test seams

  • binaries: unit tests on temp folders with fixtures::executable scripts that print a version: first on PATH, a symlink to the same file is not shadowing, same build is not shadowing, another build or none is.
  • client::connect / running: server tests over a real socket (src/server/tests.rs). Welcome carries the server's binary. A refusal message names the pid and saaio --stop. running against a fake protocol-8 listener reports server: None.
  • output::update: TOON snapshots with and without others.
  • App::warn, keys and chrome: app tests plus golden screens of the dialog and title line (SAAIO_UPDATE_GOLDEN).
  • send: CLI test in tests/cli with SAAIO_MASTER=1 and no SAAIO_PROOF.
  • E2E: the repro rerun with 0.1.1 first on PATH and this build behind it, plus a running 0.1.2 server.

Assumptions

  • A different file on PATH with the same build is not a mismatch: copies of one build behave alike.
  • The UI compares the full build (version and commit), so two source builds of different commits warn. saaio update compares versions only, since a release's commit is not known before install.
  • The PATH probe runs once when the UI starts. Up to 1 s is added only when another saaio comes first.
  • The dialog shows once per UI start. The title line stays until the UI quits.
  • The UI warns and does nothing else. It does not stop or restart the server itself.
  • saaio update lists servers of every registered store, not only the current one.
  • Paths in messages use ~ for the home folder.

Open questions

  1. Offer a restart in the dialog? The UI could offer r: stop this server (without ending flows) and start one from this binary, which is what saaio --stop plus saaio does by hand. Recommended: no for this PR. Warn only, as asked. Add it to the roadmap if the warning proves to be a chore.
  2. Make panes run the server's saaio? The server could put a private folder holding a saaio link to its own binary first on each pane's PATH. Agents' saaio send would then always match the server, which removes the PATH case for agents entirely. Recommended: roadmap item, not this PR.
