design-code / phase 2 - pick an approach

flow ui: who opens a worker's pane, and who owns the terminals?

All three approaches build the same screens (design canvas) with the same crates. They differ in how a flow start run inside the master pane gets a new pane opened, and in which process owns the pseudo-terminals.

new modified unchanged

What exists today, and what is decided

  • flow start refuses outside tmux (main.rs:277), makes the worktree, runs .flow/setup, then opens a tmux window and records its id as Workspace.window (main.rs:324-338, workspace.rs:69, launch.rs:97).
  • The worker command comes from an agent template; Claude Code is claude -n {name} --session-id {id} {prompt} (config.rs:63). The flow id is the Claude session id, so claude --resume {id} can bring a worker back.
  • State reaches flow only through the log: workers call flow report, readers fold it (fold::board, fold.rs:36). The board mod polls flow status --json every 2 s.
  • The store is global, one log per flow under $FLOW_HOME (store.rs:17). main.rs is the only place that touches env, clock and stdout.
  • Decided: own multiplexer in this crate, not herdr or tmux. The master stays, as one Claude session that coordinates through the flow CLI.
  • Decided: the TUI is flow ui; bare flow stays the agent home.
  • Decided: the tmux path is replaced: workers always run inside flow ui.
  • Decided: one flow ui shows the flows of all repos.
  • Extensions and the theme file come later; colors are named tokens from day one.

The same in every approach

  • Crates: ratatui + crossterm to draw, portable-pty for the pseudo-terminals, a terminal emulator chosen by a spike in milestone 1 (vt100 + tui-term against alacritty_terminal, both run against a real Claude session).
  • The sidebar, board and status line read the same fold::board the CLI prints; peek reads the worker's Claude transcript file, independent of the emulator.
  • Build order: one pane with the bottom bar, then several panes and the sidebar, then workers from flow start, then peek, board, new flow and rail, then restore after a restart.

A. One process; flow ui opens panes for what the log says should run

flow start stops opening anything: it records the flow and its workspace, as it does today, minus the window. Inside flow ui a reconciler looks at the board and opens a pane for every unfinished flow that has a workspace and no live pane: a fresh agent the first time, claude --resume {id} after a restart. The pane host owns the PTYs behind a narrow interface, so it can move into a daemon later without touching the UI.

Touches

  • new src/ui/ (app, host, reconciler, sidebar, board, peek, theme tokens)
  • main.rs: Ui subcommand; start loses the tmux check and the window
  • launch.rs/workspace.rs: tmux argv and window functions go
  • Workspace.window stops being written; old logs still fold

Fit

  • Same rule as today: everything goes through the log, readers fold it (CLAUDE.md data flow).
  • Start and restore are one code path: "unfinished, has a workspace, no pane".
  • No protocol between the CLI and the UI to design or version.
Costs. flow start cannot say "pane opened" - it says "recorded; flow ui opens it", and a pane appears within the poll interval (about half a second). A failure to spawn shows in the UI, not in the CLI output. If flow ui crashes, every session dies with it until it restarts and resumes them. Without flow ui running, nothing starts.

B. One process with a control socket, like $TMUX

flow ui listens on a Unix socket and sets FLOW_UI in every pane. flow start finds the socket, asks the UI to open the pane and records the pane id the way it records a tmux window id today.

Touches

  • everything in A, plus a socket server, a client in flow start and a small request/response format
  • Workspace.window becomes the pane id

Fit

  • Closest to today's shape: start opens, gets an id, records it (main.rs:331).
  • flow start reports a spawn failure right away.
Costs. A second channel next to the log, with its own format to keep compatible. Restore after a restart still needs A's "open what should run" logic, so there are two ways a pane gets opened. flow start outside flow ui must fail or fall back to recording only - which is A again. Same crash exposure as A.

C. A server owns the sessions now; flow ui is a client

recommended

flow server runs in the background, owns every PTY and emulator, and streams screen updates to flow ui over a Unix socket. Panes open the A way: the server's reconciler opens what the log says should run, so flow start still only records. Closing or crashing the UI leaves the sessions running; you reattach later, also over SSH.

Touches

  • everything in A, plus a daemon lifecycle (start, find, stop, stale sockets) and a screen protocol: cell diffs, input, resize, focus

Fit

  • The most robust: sessions survive the UI.
  • Opens the door to remote use later.
Costs. The largest by far: a daemon lifecycle and a screen protocol, and every bug has two processes to look at. Resource use stays small if the server sends only the focused pane's changed cells and the client asks for nothing it does not draw; idle panes cost only the emulator parsing their output.

Recommendation: C, opening panes the A way

You asked for the most reliable and lightweight result, whatever the build cost. In A, one panic in drawing or key handling kills every agent mid-tool-call; --resume brings back the conversation but not a running test or a half-applied edit. C keeps that risky code in the client and leaves the server small: PTYs, emulators, the reconciler and a socket. It is the split tmux has proven for decades, and closing the terminal window no longer ends your agents. From A it keeps the log as the only way a pane gets opened, so flow start, the agents and --json keep their contracts and start and restore stay one code path. B adds a second channel without the crash isolation.

Milestone 1 still starts with one pane, but already split: flow server plus flow ui, so the protocol is proven on the emulator spike rather than added later.
