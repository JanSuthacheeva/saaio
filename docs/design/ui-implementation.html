flow ui: a session server that owns the terminals, and a client that draws them

Screens: design canvas. Approaches: .lavish/tui-approaches.html. No method bodies here, only units, signatures and the order of calls.

new modified unchanged

1. Decision recap

flow server is a small background process that owns every pseudo-terminal, its terminal emulator and the Claude process inside it, and opens panes for what the log says should run. flow ui is a client that sends keys and sizes over a Unix socket and draws the screens, the sidebar and the views; when it crashes or you close the window, the agents keep running.

  • Approach C, with A's rule: the log is the only way a pane gets opened. flow start records; the server's reconciler opens. Start and restore are one code path.
  • flow ui is the command; bare flow stays the agent home. One UI shows the flows of all repos.
  • The tmux path goes: no tmux check, no window, no tmux kill-window.
  • Reliable and lightweight beats build cost. Once usable, flow ui is home and the Claude Code board mod is retired; the CLI and --json stay for agents.
  • Extensions and the theme file come later; colors are named tokens now.

2. Structure overview

The UI never touches a PTY, and the server never draws. Both sides speak only proto.rs; the server reads the store, the UI reads only Claude transcripts for peek. The arrow from App to Server is the socket.

src/server/host.rsnewI/O

Owns the panes: a PTY, the child process and its Terminal each. The seam a remote host could implement later. Depends on: portable-pty, Terminal.

pub enum HostEvent { Output(PaneKey, Vec<u8>), Exited(PaneKey, Option<u32>) }

impl Host {
    pub fn new(size: Size, events: Sender<HostEvent>) -> Host;
    /// Spawns the child in a new PTY with a reader and a waiter thread; on Err the pane is kept as Failed.
    pub fn open(&mut self, spec: PaneSpec) -> Result<()>;
    /// Keeps a pane that could not be opened, with the reason shown in it.
    pub fn fail(&mut self, key: PaneKey, reason: String);
    /// Feeds output into the pane's Terminal and writes the Terminal's replies (DA, DSR) back to the PTY.
    pub fn feed(&mut self, key: &PaneKey, bytes: &[u8]);
    /// Writes input to a running pane; Ok without writing to an exited one.
    pub fn write(&mut self, key: &PaneKey, bytes: &[u8]) -> Result<()>;
    /// Every pane to the same size, PTY and Terminal.
    pub fn resize(&mut self, size: Size);
    pub fn exited(&mut self, key: &PaneKey, code: Option<u32>);
    /// SIGHUP to the child's process group, SIGKILL after 3 s; the pane is gone once it exits.
    pub fn close(&mut self, key: &PaneKey);
    /// The pane's rows: all when full, else the damaged ones; scrolled back by history lines.
    pub fn frame(&mut self, key: &PaneKey, full: bool, history: Option<u32>) -> Option<Frame>;
    pub fn panes(&self) -> Vec<PaneInfo>;
}

7. Test seams

  • proto: round trip of every message; split reads; oversize and garbage are errors, clean EOF is None.
  • Terminal: byte sequences in, rows, cursor, modes and replies out (golden), incl. wide chars, scroll regions, DA/DSR.
  • Host: real sh in a PTY: output arrives, stty size follows resize, exit code arrives, close kills a process group that ignores SIGHUP.
  • reconcile, worker_spec, MasterRecord::spec, layout::areas, Router::route: pure table tests.
  • StoreWatch: temp store; append, beat, remove, and the 5 s refold.
  • App: messages and inputs in, effects out; drawing with ratatui's TestBackend against the canvas screens.
  • peek::tail: fixture transcripts, including a truncated last line.
  • Server: integration test with a temp FLOW_HOME, a cat agent from config.toml, a real socket: attach, type, see frames; flow start opens a pane; kill and restart resumes it.
  • End to end, by hand: a real Claude master and two workers, detach, reattach, kill the server, restart.

8. Assumptions

  1. Plain threads and channels; one thread owns the Host. No async runtime.
  2. Wire format: u32 length + postcard. Smaller and faster than JSON lines.
  3. Only the focused pane streams: changed rows only, at most 60 frames a second. Every pane has the size of the pane area.
  4. The server checks the store every 500 ms by size and mtime, and refolds at least every 5 s so heartbeat ages stay right.
  5. An exited pane keeps its last screen and is not reopened on its own; C-space r resumes it.
  6. Keys reach the pane as raw bytes; the outer terminal mirrors the pane's paste, mouse and cursor-key modes.
  7. flow start without a running server records the flow and says it opens when flow ui runs.
  8. One UI attached at a time: a new flow ui takes over and the old one exits with "attached elsewhere".
  9. flow remove waits up to 5 s for the pane to close, then tears down the worktree anyway and reports "timed out".

9. Decided in review

  • The server stops with C-space Q in the UI (with a confirm) or flow ui --stop; never on its own.
  • The master runs in the directory of the first flow ui, remembered in master.json.
  • The master uses the default agent from config with the name master and no prompt, so tests can swap it for cat.
