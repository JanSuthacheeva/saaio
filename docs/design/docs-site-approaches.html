saaio.dev Docs Site

A searchable docs site at saaio.dev, generated from docs/*.md and README.md on every merge to main. The master also passed on that the docs should read like the Laravel documentation. Two decisions on this page: how the site is built and how the rewrite is cut.

What exists today

  • 12 user pages: README.md (pitch, screenshot, the install snippet pinned to --tag v0.2.1) and 11 in docs/, about 3,000 lines. docs/README.md is a table of the pages in reading order. docs/HANDOVER.md and docs/design/*.html are for contributors and stay off the site.
  • Links are relative and work on GitHub: configuration.md#ui, media/saaio-ui.png, and 9 that leave docs/ (../examples/config.toml, ../CHANGELOG.md, ../ROADMAP.md). README links docs/install.md and examples/config.toml.
  • Anchors are GitHub's heading slugs, around 120 of them. README uses a GitHub alert (> [!IMPORTANT]).
  • pulldown-cmark 0.13 is already a dependency (the UI's peek renders Markdown). It parses GitHub alerts (ENABLE_GFM) and renders HTML.
  • CI is ci.yml (fmt, clippy, test, deny) and release.yml; every action is pinned to a commit. Nothing deploys a site yet.
  • The current voice comes from plan-flow-docs-voice.md (ripgrep/zoxide models, "every page opens with something to run").

A constraint found while checking: a second Cargo package anywhere in the repo breaks the documented install. I tried it in a scratch repo: cargo install --git searches the whole repo and fails with multiple packages with binaries found: app, site. So a Rust generator can't be its own crate or an xtask. It has to be a feature-gated binary of saaio itself, which cargo install skips.

Decision 1: the generator

A. Our own generator, search by Pagefind

Recommended

A small Rust binary, saaio-site, under src/bin/site/. It only builds with --features site, so users never compile it. It renders the pages with the pulldown-cmark we already use, gives headings GitHub's slugs, and rewrites every link. A link to a page goes to its URL on the site; anything else in the repo goes to its file on GitHub. Broken links and anchors fail the build. The template and CSS are the jasu.dev look, hand-written. Pagefind (one pinned binary) indexes the HTML for search.

Benefits
  • Links behave the same everywhere: one rule for all of them, checked on every PR. No link in the Markdown changes.
  • Same slugs and alerts as GitHub, from the parser saaio already uses.
  • The jasu.dev look exactly, with no theme to fight or upgrade.
  • Tested with cargo test, linted with clippy, like the rest of saaio.
  • Pagefind is the strongest static search: it indexes headings and shows excerpts, the index loads in chunks, and it needs no server.
Costs
  • We own roughly 500 lines plus CSS, nav and the search UI glue.
  • A second binary in a crate whose rule is "a library with a thin binary". CI runs clippy and the tests with --all-features.
  • Pagefind is a pinned download in CI, checked by SHA.

Touches: Cargo.toml ([features], [[bin]]), src/bin/site/*, site/ (template, CSS), .github/workflows/docs.yml, ci.yml (--all-features), CLAUDE.md, CONTRIBUTING.md.

B. mdBook with a custom theme

The rust-lang docs tool (0.5.4, installed as a pinned binary). It already has search, a theme toggle, a mobile layout and .md to .html link rewriting. book.toml points at docs/, and the jasu.dev look comes from overriding its handlebars theme and CSS.

Benefits
  • Almost no code. Search, nav, toggle and print come with it.
  • A well-known Rust tool, maintained by the Rust project.
Costs
  • A SUMMARY.md that repeats the docs/README.md table and shows on GitHub as a stray page.
  • The 9 links out of docs/ break on the site. They'd become absolute GitHub URLs, or need a preprocessor, which is code again. README can't be the home page without rewriting its docs/ links.
  • A missing anchor isn't caught. That needs mdbook-linkcheck, a third tool.
  • An overridden index.hbs breaks on mdBook upgrades. The page shape stays mdBook's (menu bar, left chapter list).
  • Its search index is one JSON file of the whole book. That's fine at this size.

C. VitePress

A Vue/Vite docs generator. It has search, a right-hand "on this page" outline (what laravel.com has), GitHub alerts, and a dead-link check out of the box. The look comes from CSS variables over its default theme.

Benefits
  • The richest default UX, and the closest to laravel.com's layout.
  • Relative .md links work, and dead links fail the build.
Costs
  • A Node toolchain in a Rust repo: package.json, a lockfile, npm advisories that cargo deny doesn't see.
  • Its slugs differ from GitHub's on edge cases unless github-slugger is wired in.
  • Same problem with links out of docs/ and with README as the home page.
  • It still looks like VitePress: the jasu.dev look only reaches as far as its CSS variables.

Hosting (one sensible option)

GitHub Pages, deployed from Actions (actions/upload-pages-artifact + actions/deploy-pages, no gh-pages branch). It runs on every push to main that touches the docs, and on demand. The custom domain is set in the repo settings, and GitHub issues the HTTPS certificate. That certificate matters because .dev is HSTS-preloaded and loads over HTTPS only. Cloudflare Pages and Netlify were rejected: they mean another account, another set of secrets and nothing gained at this size.

Decision 2: the Laravel-style docs

What laravel.com/docs does, and what it means here. Every page starts with Introduction and opens with a nested table of contents. Sections build from the common case to the advanced one. The prose is friendly and says why before how, with a code example right after each concept, and uses > [!NOTE] / > [!WARNING] callouts. Laravel's own Markdown source uses exactly these. On GitHub, the TOC is a plain nested list of #slug links, and the callouts are GitHub alerts, which it renders natively. So nothing GitHub-only or site-only goes into the Markdown.

  • Rewritten: all 11 docs/*.md pages. The guide pages (install, ui, flows, configuration, agents, themes, repository, troubleshooting) get the full treatment: Introduction, why-then-how prose, an example per concept. The reference pages (cli, json, files) get the structure (Introduction, TOC, callouts, common before advanced) and keep their lookup tables. docs/README.md becomes the docs index page.
  • Kept close to as is: the root README.md, which is GitHub's landing page and the site's home. It gets one callout pass at most.
  • Superseded: the docs-voice rule "every page opens with something to run" becomes "every page opens with an Introduction that shows something to run". The other rules stay: "you", no em dash, tables only for lookups, facts unchanged.
  • Unchanged: every heading that something links to keeps its slug, or every link to it moves with it. The generator's link check proves this on both versions.

How to cut it

Recommend 2a
  1. 2a. Two PRs in sequence. This flow ships the site with the current text. A second flow then rewrites the pages, and its diff is prose only, with the site's link check guarding every anchor. Each diff can be reviewed on its own merits, and the site goes live sooner.
  2. 2b. One PR, two milestones. Site first, then the rewrite on the same branch. That's one review of about 3,000 changed lines of prose plus the generator.

Recommendation

A + GitHub Pages + 2a. The requirements that matter most here are links that work on the site and on GitHub, and the jasu.dev look kept exact. A meets both by construction, where B and C meet them with workarounds. A also gets tested and linted like the rest of saaio. The extra code is small and owned. Splitting the rewrite off keeps two very different reviews apart.
