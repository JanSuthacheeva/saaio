You picked all nine findings from the design review. Most of them are local fixes with only one sensible shape: names cut with split, a plural, a hint string. Two decisions have real structural options. One is how a single focus look (item 9) and a single dialog frame (item 4) get shared. The other is what fills the board's detail panel (item 8).

What exists today

  • Focus is drawn in four places, each its own way. The sidebar paints ui.selection over a lit row (sidebar.rs:173) with a ▌ in the flow's state color (sidebar/rows.rs:76). The rail copies that (rail.rs:51,77). A board card gets an accent rounded border (board/cards.rs:238). New flow uses an accent border on the text box (newflow/view.rs:105), a bold label on the focused radio row (:130) and an accent (•) (:118).
  • Dialogs: help, stop, confirm, not-running and no-session go through draw_dialog (dialog.rs:10). It draws a bordered paragraph with no vertical padding and no dimming. New flow draws its own frame (newflow/view.rs:26), and only it dims the screen (app/draw.rs:154).
  • Chrome: App::areas chooses Chrome::Solo while there are no workers (app.rs:156, layout.rs:78), so the bottom bar turns into the sidebar when the first worker starts.
  • Narrow width: the card label is painted over the name with set_span and is not fitted (board/cards.rs:254). The board footer is one fixed line (board.rs:142). The sidebar is always 40 columns (layout.rs:6).
  • The detail panel has the data it needs already: FlowView.answer holds the last turn's whole closing message (view.rs:39), and PeekCache tails the transcript of the flow under the sidebar cursor (peek.rs:166, ui.rs:136).

A. Two shared pieces: focus.rs and a Dialog

A new ui/focus.rs owns the one focus look: it paints the selection fill over an area and draws a copper ▌ down its left edge. The sidebar, the rail, the board cards and new flow's fields all call it, so none of them draws focus itself. dialog.rs gets a Dialog struct (title, body, keys) with one render that dims the screen, clears, frames with padding and draws the key row under a ├─┤ rule. Every dialog is built on it, new flow included.

Touches

new ui/focus.rs; dialog.rs, sidebar/rows.rs, rail.rs, board/cards.rs, newflow/view.rs, app/draw.rs; golden files.

Costs

One more module. Every dialog's text moves into Dialog fields, so the stop and help bodies are rewritten. Golden files change across the board, which is expected.

Fit: one responsibility per file (CLAUDE.md). Focus becomes a noun module, like fit.rs is for text in columns. It keeps the Elm core untouched: App still only says what is focused, and the widgets draw it.

B. Theme tokens only

Add ui.focus_bar and ui.focus_fill to UiTokens, and fix each widget and each dialog where it stands to use them, adding the same padding and dim calls in each draw function.

Gains

No new module, and the smallest diff per file.

Costs

The bar, the fill and the dialog padding are each written out in five places, which is how they drifted apart in the first place. Theme files gain keys users could set, which is public surface.

Item 8: what fills the detail panel

The panel has about 20 free rows under a 3-line timeline. In every option the steps move into the header strip under the flow's name, and the timeline keeps the left column.

a. The last answer (recommended). The right column shows FlowView.answer, the worker's whole closing message, wrapped and cut from the top to fit, with decisions above it when there are any. It is already in the board, so it needs no I/O and no new state. It is the text you would read before jumping in.

b. The live transcript. The same tool calls and text the peek shows, for the selected card: App::peeked would follow the board selection. It is livelier, but it reads the transcript every few ticks while the board is open, and it repeats what the peek already does.

c. More of the timeline. The timeline spans the full width with decisions under it. Nothing new, but most flows have fewer than 15 entries, so the panel stays half empty.

Recommendation

A with 8a. The findings come from five widgets each drawing focus and frames their own way. Sharing the colors (B) fixes today's look but not the cause. A puts the look in one place, so a later dialog cannot drift, and 8a fills the panel with what you actually want to read using data flow ui already has.
