Kinds of flows: where the workflows live

Feature, fix and research flows, each with its own phases, skills, first prompt and branch type. Pick one approach below, and answer the four shared questions at the end.

What exists today

  • One workflow. Config.workflow is the top-level [[phases]], the built-in four otherwise (src/workflow.rs:64, src/config.rs:46).
  • Phase names are recorded, skills are not. saaio start and saaio new write the names into Started.phases (start.rs:92, new.rs:33); fold reads them from there (fold.rs:196).
  • The hook maps skills with today's config. saaio hook calls translate(payload, &config.workflow) for every flow (hook.rs:239), so a config edit already changes what a running flow's skills mean.
  • The first prompt belongs to the agent. Built-in claude has /ship-feature {request}, codex $ship-feature {request}; [worker] prompt fills in for agents without one (config.rs:214, config.rs:280). Only the sigil differs.
  • "kind" already means branch type. saaio start --type is stored in a field named kind and picked by pick_kind from the repo's [branch] types (start.rs:44, branching.rs:47); the dialog's type row is NewFlowForm.kind (newflow.rs:37). These get renamed to branch_type.
  • A branchless worktree fits. Workspace.branch is already an Option, and remove and clear skip a flow without one (retire.rs:147).
  • A flow is done only by its merge request (fold.rs:437).
  • master.md is versioned: changing it adds master-v13.md as the earlier default (src/server/master-v*.md).

A. Kinds in config, looked up by name

config.toml gets [kinds.<name>] tables, with feature, fix and research built in. Started records the kind's name next to its phase names. saaio hook reads the flow's kind from its log and maps skills with that kind's workflow from today's config.

Gains

  • Smallest log change: one optional field.
  • Same lookup the hook does today, per kind.

Costs

  • Rename or remove a kind in config and its running flows stop moving through steps.
  • Editing a kind's skills mid-flow can point a skill at a phase the flow never recorded.
  • The hook reads the flow's log before translating, an extra read per hook call.

B. Kinds in config, the workflow recorded in the flow Recommended

Same config as A. Started records the kind and its whole workflow, names and skills. Config is read once, at start; afterwards the flow's own log says what each skill means, so the docs' promise "a running flow keeps its phases" becomes true for the skills too.

Touches: as A. Started.phases: Vec<Phase> gains a sibling skills (or becomes Vec<PhaseSpec> with a reader that still takes bare names); old logs fall back to today's config, as now.

Gains

  • A running flow never changes meaning under a config edit, rename or removed kind.
  • The hook already folds the flow to decide what changes (fold::changes); it takes the workflow from there.
  • Fits the existing rule "fold reads phases from the log, never from config" (workflow.rs doc, CLAUDE.md).

Costs

  • A wider log change: the skills ride in every started line, and the reader keeps old lines working.
  • The hook must fold before it translates; today it translates first.

C. Three kinds in code

An enum Kind { Feature, Fix, Research } with fixed workflows, prompts and branch types; only feature stays configurable through today's [[phases]] and [worker] prompt. No [kinds] in config.

Gains

  • Least code and no new config surface.
  • --kind is a clap ValueEnum, so completions list the kinds.

Costs

  • Someone with their own skills can change the feature workflow but not fix or research, nor add a "docs" kind.
  • Contradicts the roadmap's "named workflows" and the configurable-workflow direction; a later move to config changes the public surface twice.

Recommendation

B. The config shape is the same as A, so the public surface is decided once. Recording the skills costs a slightly wider started line and buys flows that keep their meaning however the config changes, which is the rule the code already follows for phase names. C is the cheapest now and the most expensive later.

Shared by all three: four questions

These are public surface or stored behaviour, so they are yours. My recommendation first in each.

  1. First prompt. A kind has a skill (feature ship-feature, fix ship-fix) and a prompt, default {skill} {request}. {skill} is written in the agent's harness syntax: /ship-fix for Claude Code, $ship-fix for Codex, bare for an agent without an adapter. The built-in agents lose their own prompt, the kind supplies it. Research has no skill in agent-skills, so its built-in prompt is plain words: Research this and answer here. Change no code and commit nothing: {request}. An agent's own prompt in config.toml still wins for every kind (it is how that agent takes input); [worker] prompt becomes the feature kind's prompt. 
    [kinds.fix]
skill = "ship-fix"
branch_types = ["fix", "bugfix", "hotfix"]

[[kinds.fix.phases]]
name = "diagnose"
skills = ["diagnose-bug"]
# implement, review, merge-request as in feature
  2. Branch type. A kind lists the branch types it means, in order; the first one the repo's [branch] types lists wins, else the repo's first type, as today. --type still overrides. Built in: feature ["feature", "feat"], fix ["fix", "bugfix", "hotfix"]. Without a repo convention the branch stays flow/<name>. The alternative, a mapping in each repo's .saaio/config.toml, is explicit but needs every repo edited before fix branches get the right type.
  3. Research. branch = false: its worktree is detached at the base (git worktree add --detach), so it can read and run the code with its own slot and setup, and leaves no branch behind; remove and clear already handle a flow without one. Its one phase is research. It never becomes done by a merge request; it ends idle with its answer, and the master says the findings are ready. The alternative is no worktree at all, in the repo's checkout like a plain session, which shares the person's working tree.
  4. Old configs. Top-level [[phases]] and [worker] prompt keep working as the feature kind's. Setting both [[phases]] and [[kinds.feature.phases]] is an error that names the line. --kind defaults to feature (a [worker] kind setting can change it); the master picks the kind from the request per master.md.
